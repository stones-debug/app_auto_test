## 二、总体结论

工程质量**明显高于同体量的个人或小团队项目**。判断依据不是"代码写得干净"，而是它已经建立了一套**能自动防止自己腐化的护栏**：

- `alembic check` 阻止模型与迁移漂移
- `generate_protocol.py --check` 阻止前后端协议漂移
- `validate_security_baseline()` 阻止带默认密钥启动
- `check:bundle` 阻止前端产物无节制膨胀

这四件事，很多有专职运维的团队都没做全。**当前的主要风险不是"有 bug"，而是"复杂度已经开始集中在少数几个文件里，且这些文件恰好是最难测的部分"。**

## 三、做得好的部分（请勿在重构中破坏）

### 1. 业务不变量下沉到数据库层

`models/execution.py` 用**部分唯一索引**区分套件级步骤与用例级步骤：

```python
Index("uq_execution_steps_suite_order",
      "execution_suite_id", "phase", "step_order",
      unique=True,
      postgresql_where=text("execution_suite_id IS NOT NULL AND execution_case_id IS NULL"))
```

`models/app_profile.py` 有 20+ 条 `CheckConstraint`，包括 `jsonb_typeof(changes) = 'array'`、`code ~ '^[a-z][a-z0-9_-]{1,63}$'`。

把"什么数据合法"交给 DB 兜底，比在应用层散落校验可靠得多。这是正确的取舍。

### 2. 并发处理是正确的

- 队列认领：`with_for_update(skip_locked=True)` + 部分索引 `idx_queue_pending (WHERE status='pending')`
- 设备/Agent 状态变更：`agents.py:112/117/326/361`、`execution_service.py:105/119/138` 均显式加行锁

配合循环外键 `devices.locked_by_execution ↔ executions.device_id` 这种高危设计，锁的使用是必要的，且用对了。

### 3. 异常处理的克制程度罕见

全仓 `backend/app` 只有 **7 处** `except Exception`，且全部 `logger.exception`。更关键的是 `worker_runtime.py:102`：

```python
except asyncio.CancelledError:
    raise
except Exception:
    # 单次数据库/调度异常只影响本轮，后台消费必须继续存活。
    logger.exception("Worker %s 处理任务异常", self.worker_id)
```

先放行 `CancelledError` 再兜通用异常 —— 这是后台任务循环的正确写法，很多人会写反。

### 4. 权限模型分层清晰

`api/deps.py` 提供了四层校验：`require_project_role` / `require_platform_admin` / `require_agent_access` / `require_device_access`。

其中 `require_device_access` 会**联查设备所属 Agent 的绑定关系**再判权，并且软注销的 Agent 其设备一并视为不存在 —— 这挡住了"猜 ID 用他人设备"这条常见攻击路径。

### 5. CI 覆盖完整

`.github/workflows/ci.yml` 四个 job，其中 `windows-agent-package` 真的跑 PyInstaller 打包 + Inno Setup 编译安装包 + 对打包后的 exe 再跑一次 `--self-check`。这条流水线价值很高。

### 6. AGENTS.md 把踩过的坑固化了

元组解包、asyncpg 事件循环不能跨 pytest、Node 18 不能装 sass、B008 不要"修复" —— 这些都是真实踩坑后的沉淀，比任何通用规范都有用。

## 四、问题清单

### P0 — 复杂度集中在最难测的位置

| 文件 | 行数 | 问题 |
|---|---|---|
| `app/api/app_profiles.py` | **1,989** | 单 API 模块，`skip_rules_batch()` 144 行、`differences()` 129 行 |
| `app/services/profile_resolver.py` | **1,101** | `resolve()` 121 行、`_build_suite()` 137 行 |
| `app/services/worker_service.py` | **1,036** | **`_mark_terminal()` 225 行**、`_build_suites_payload()` 155 行 |
| `frontend/src/views/Suite.vue` | **1,353** | 套件 + 用例 + 模块折叠 + 批量选择全在一个 SFC |

**最需要优先处理的是 `_mark_terminal()`（225 行）。** 它是全系统正确性最关键的一段，要同时处理：

- 状态优先级 `error > failed > stopped > skipped > passed`
- N/A 不进任何成功率分母
- 套件前置失败时，套件内用例置 `skipped`，但套件后置**仍要执行**

这三个规则交织在一个 225 行、且与数据库 IO 耦合的函数里，意味着**它实际上无法被有效单元测试**。

建议：抽出与 IO 解耦的纯函数 `compute_suite_stats(...)`，单独对它做表驱动测试；`_mark_terminal()` 退化为"取数 → 调纯函数 → 落库"。

同理：
- ~~`schemas/execution.py:_validate_run_parameters()` 249 行、`schemas/element.py:_validate_locator()` 162 行、`schemas/smart_locator.py:_uiautomator_expressible()` 127 行。~~ **此处为原报告度量错误**：误把函数起始行号当成函数长度。复核后三个函数分别约 **6 / 13 / 12 行**，逻辑集中且已有 schema 测试，不构成超长函数问题，也不需要为拆分而拆分。
- `app/api/app_profiles.py` 建议拆为子路由包：`app/api/app_profiles/{nodes,overrides,skip_rules,releases,differences}.py`。

截至 2026-08-30：终态纯函数和表驱动测试已在 Step 9 完成，`_mark_terminal()` N+1 已在 Step 10 批量化；APP 档案路由、解析器和 `Suite.vue` 分别在 Step 11～13 完成拆分。当前 `profile_resolver.py` 为 605 行，数据库加载和节点纯逻辑已拆为 264/253 行模块；`Suite.vue` 已降至 408 行。上述 P0/P2 结构项保留为历史问题，不再重复立项。

### P1 — 安全加固（需要确认或补强）

**1. `/metrics` 端点无鉴权** — `main.py:96`

```python
@app.get("/metrics")
async def metrics():
    """方案 §10.5：轻量指标暴露（内网；生产应受网络策略保护）。"""
```

注释把安全寄托在外部网络策略上。指标端点通常会泄漏执行量、失败率、Agent 数量等运营数据。建议加 `X-Internal-Token` 校验，或至少在 `environment == "production"` 时强制绑定 `127.0.0.1`。

**2. 内部令牌使用 `!=` 比较** — `api/internal.py:15`

```python
if x_internal_token != settings.internal_token:
```

字符串 `!=` 存在理论上的计时侧信道。建议统一改用 `secrets.compare_digest`（Agent Key 校验处同理）。

**3. Agent WebSocket 缺少连接级防护** — `ws/routes.py:148`

`agent_ws` 在 `register` 成功**之前**就 `await websocket.accept()`，且未见消息体大小上限与频率限制。已有 `validate_agent_message` 做协议校验（这部分做得对），但建议补：

- 单帧大小上限（防止超大 payload）
- register 前的消息数限流
- 未 register 连接的最大存活时长

否则匿名连接可长期占用网关资源。

**4. CORS 缺少"通配"护栏** — `main.py:70`

当前 `allow_origins` 是白名单，`allow_methods=["*"]` + `allow_credentials=True` 的组合是可接受的。但建议在 `validate_security_baseline()` 中增加一条：

```python
if "*" in settings.cors_origins:
    problems.append("cors_origins 不能包含通配符 *")
```

防止部署时为图省事改成 `["*"]` 而直接出事。

**5. 安全基线在非 production 下完全不生效** — `config.py:129`

```python
if settings.environment == "development":
    return
```

`environment` 默认值就是 `development`。整套校验（默认密钥、弱口令、短密钥）只在显式设为 production 时才跑。开发便利性是合理的取舍，但必须确保**部署脚本 / 容器编排强制注入 `environment=production`**，否则整套护栏形同虚设。

### P2 — 一致性与工程卫生

**6. `main.py:103-104` 缺少空行**

```python
    return PlainTextResponse(render_metrics(), media_type="text/plain; version=0.0.4")
@app.get("/api/health")
```

模块级定义之间应有两行空行。ruff 未报出，建议手修。

**7. 前端生成物缺少 drift 检查（原报告误报，已关闭）**

`frontend/src/api/generated/registry.ts` 虽位于前端，但唯一生成器 `agent/scripts/generate_protocol.py --check` 会同时校验：

- `backend/app/protocol/action_registry.json`；
- `backend/app/schemas/generated_case_params.py`；
- `frontend/src/api/generated/registry.ts`。

CI 的 Agent job 已执行该命令，因此前端生成物已经在同一门禁中覆盖，不需要在 frontend job 再重复增加一条。

**8. `vuedraggable@^4.1.0` 仅保留为依赖观察项**

当前 `CaseStepEditor.vue` 与 `Suite.vue` 正常使用 `vuedraggable@4.1.0`，现有 Vitest 和生产构建未出现 Vue 3.5 兼容缺陷。没有真实故障、维护阻断或安全问题时不迁移到 `vue-draggable-plus`；后续仅在依赖升级失败或拖拽行为出现可复现问题时重新评估。

**9. 错误响应缺少机器可读的错误码**

目前大量 `HTTPException(detail="中文文案")`，前端若要按错误类型分支就只能匹配文案 —— 很脆弱。仓库内部已有 `PROTOCOL_ERROR` 这类做法（`ws/routes.py:165`），建议推广为统一的 `{code, message, detail}` 结构。

**10. 疑似废弃目录与提交噪音**

- `backend/app/executor/` 只有三个空 `__init__.py`，全仓无代码引用；Action/Assertion Registry 的权威实现位于 `agent/executor/`，该目录已确认可删除。
- Git 实际只跟踪 `session-ses_fe2f.md`；原报告关于 `session-ses_fdb1.md` 也已入库的描述不准确。会话文件应移除并用根规则 `/session-*.md` 忽略。
- 根目录 `pyproject.toml` 当前是未跟踪文件，不属于基准提交；在明确 monorepo 工具职责前不应提交。

建议清理或加入 `.gitignore`。

### P3 — 可观测性

**11. 跨进程链路缺少 trace_id**

执行链路横跨 FastAPI → Worker → Agent 三个进程，目前只能靠 `execution_id` 人工串联日志。建议引入 trace_id 并在三侧透传，否则线上排查一次执行失败要在三份日志里手工对齐时间戳。

**12. 日志表清理已经覆盖（原风险关闭）**

`cleanup_service.cleanup_old_logs()` 已按 `log_retention_days` 对 `ExecutionLog.created_at` 执行批量 DELETE 并提交；Worker runtime 的每日清理任务同时调用报告和日志清理。该项无需新增实现，后续只需保留现有测试和清理任务监控。

## 六、一句话总结

**架构决策和工程护栏是优秀的，问题出在"局部复杂度已经开始失控，而失控点恰好在最难测的终态汇算逻辑上"。** 先做第 1 项（抽纯函数 + 表驱动测试），再做第 2 项（拆包），其余可以按业务节奏排期。
