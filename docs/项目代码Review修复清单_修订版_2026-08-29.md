## Step 7 — 修复多套件执行终态优先级

**目标**：执行结果与套件顺序无关，严格遵循 `error > failed > stopped > skipped > passed`。

### 7.1 Agent 聚合逻辑

涉及文件：

- `agent/executor/test_runner.py`
- `agent/main.py`
- `agent/tests/test_main.py`
- `agent/tests/test_executor.py`

代码任务：

1. 将 Agent 当前 `_aggregate_status()` 改为可公开复用的纯函数，例如 `aggregate_statuses()`；或移动到 `agent/executor/status.py`。
2. `TestRunner.run_suite()` 与 `AgentApp._run_execution()` 必须使用同一个聚合函数。
3. `_run_execution()` 收集所有套件结果后一次聚合，禁止在循环中覆盖 `overall`。
4. 顶层执行不保存 `skipped` 时，明确映射规则：全部套件 N/A/`skipped` 应按权威文档确定为 `passed` 或 `error`，并同步文档与测试；不得依赖当前循环默认值碰巧得到 `passed`。

必须新增的表驱动测试：

- `[error, failed]` 与 `[failed, error]` 都得到 `error`。
- `[failed, stopped]` 与 `[stopped, failed]` 都得到 `failed`。
- `[passed, skipped]` 的执行级映射符合权威口径。
- 多套件结果的任意排列得到相同终态。

### 7.2 FastAPI 服务端兜底

涉及文件：

- `backend/app/ws/handlers.py`
- `backend/tests/test_ws.py`
- `backend/app/schemas/ws.py`

代码任务：

1. `handle_execution_result()` 不应只在 Agent 上报 `passed` 时检查已落库子节点。
2. 将 Agent 终态与 `_stored_execution_terminal()` 返回值按统一优先级合并；Agent 上报 `failed/stopped` 也不能覆盖已落库的 `error`。
3. `CaseStatusIn`、`SuiteStatusIn`、`StepResultIn` 的状态字段收紧为 `Literal`，非法状态返回 `PROTOCOL_ERROR`，不能静默转换为 `running` 或写入任意字符串。
4. 防止终态节点被迟到的 `running` 消息回退；状态转换需要显式白名单或 CAS 条件。

### 7.3 Worker 最终汇总兜底

涉及文件：

- `backend/app/services/worker_service.py`
- `backend/tests/test_worker.py`

代码任务：

1. `_mark_terminal()` 最终写报告前，再按已落库的套件/用例/步骤终态合并顶层执行状态。
2. 处理包含 `pending/running` 子节点的异常终态：先按是否执行过归并为 `skipped/stopped/error`，再统计，禁止 `_aggregate_status()` 对未知状态直接返回 `passed`。
3. 增加“套件含 passed 用例但 teardown 仍 pending，执行被停止”场景，套件不得被汇为 `passed`。

建议提交：`feat(agent): Step 7 修正多套件执行终态优先级`

## Step 8 — 补齐安全加固

### 8.1 WebSocket 实际字节限制

涉及文件：

- `backend/app/ws/routes.py`
- `backend/app/core/config.py`
- `backend/start-backend.ps1`
- `backend/tests/test_ws.py`
- `docs/部署任务清单.md`
- `docs/APP自动化测试平台_详细架构实施方案.md`

代码任务：

1. 文本消息使用 `len(text.encode("utf-8"))`，二进制消息使用 `len(payload)`。
2. 测试覆盖 ASCII、中文、Emoji 和二进制边界：等于上限放行，超过上限关闭 1009。
3. `agent_ws_max_frame_bytes`、注册消息数、注册超时使用 Pydantic `Field(gt=0)` 限制非法配置。
4. `start-backend.ps1` 启动 Uvicorn 时传入与应用配置一致的 `--ws-max-size`，使超大消息在 ASGI 应用完整缓冲前被拒绝。
5. 权威启动命令和部署清单同步 `--ws-max-size`；说明直接绕过脚本启动 Uvicorn时也必须配置该参数。
6. 保留应用层检查作为纵深防御，但文档不得再把它描述为网络入口“帧限制”。

### 8.2 内部令牌强度

涉及文件：

- `backend/app/core/config.py`
- `backend/tests/test_security.py`
- `backend/.env.example`
- `docs/部署任务清单.md`

代码任务：

1. production 环境要求 `internal_token` 至少 32 字符且不能为默认值。
2. `weak_secret_names()` 与 `validate_security_baseline()` 复用同一个判定函数，避免告警和阻断标准漂移。
3. 测试覆盖空值、1 字符、31 字符、32 字符、默认长值和非 ASCII 长令牌。

### 8.3 文档纠正

- Prometheus 不在本机时不能启用“仅 loopback”并期待远程直连；应使用网络白名单、反向代理鉴权或在本机部署采集代理。
- WebSocket 在当前“连接后发送 register 消息”的协议下必须先 `accept()` 才能收消息；不要把 `accept` 本身列为漏洞，真正风险是未注册连接的时长、数量和消息资源上限。

建议提交：`feat(backend): Step 8 完成WebSocket与内部令牌加固`

## Step 9 — 抽离终态汇算纯函数

**目标**：先提升可测性，保持数据库行为不变。

新增文件：

- `backend/app/services/execution_summary.py`
- `backend/tests/test_execution_summary.py`

调整文件：

- `backend/app/services/worker_service.py`

纯函数建议：

- `aggregate_statuses(statuses) -> str`
- `merge_execution_status(agent_status, stored_statuses) -> str`
- `merge_case_status(input, terminal_status) -> CaseMergeResult`
- `compute_counts(statuses) -> Counts`
- `rate_percent(numerator, denominator) -> Decimal`
- `compute_exclusion_summary(target_types) -> ExclusionSummary`

约束：

- 新模块禁止导入 SQLAlchemy，禁止 IO。
- 纯函数只接受不可变值/数据类，不直接修改 ORM 对象。
- Worker 侧暂时保留旧函数 re-export，避免一次性扩大改动。
- `fail/failed` 两种断言状态先在输入边界规范化为 `fail`，内部不继续传播双值。

测试矩阵至少覆盖：

- 状态所有优先级及不同排列顺序。
- 步骤失败、断言失败、执行未开始、部分开始后停止。
- `[passed, skipped]` 成功率为 100%，N/A 不进分母。
- 分母为 0 时成功率为 0。
- pending 子节点不会被误判为 passed。

建议提交：`feat(backend): Step 9 抽离终态汇算纯函数`

## 数据库访问层重构统一设计

### 目标与非目标

目标：把运行时代码中的 SQL 构造、ORM 持久化、锁查询和批量聚合统一收口到 `backend/app/repositories/`，形成稳定的调用方向：

```text
API / WebSocket / Worker Runtime
                ↓
Service（业务规则、事务、错误映射、外部副作用编排）
                ↓
Repository（SQL、ORM 持久化、锁、分页和聚合查询）
                ↓
SQLAlchemy AsyncSession / PostgreSQL
```

本轮明确不做：

- 不修改 REST 路径、请求体、响应体、状态码和 OpenAPI 业务 schema。
- 不修改 Agent / 前端 WebSocket 消息结构。
- 不修改数据库表、索引、约束和 Alembic revision 链。
- 不引入通用 `BaseRepository`、ORM 包装框架、Repository 类继承或 Unit of Work 类。
- 不把 Alembic `op.*`、测试数据准备 SQL 移入 Repository。
- 不在“移动查询”的同时调整业务筛选、权限、排序、软删除或状态机语义。

### 目标目录与依赖规则

```text
backend/app/
├── repositories/
│   ├── __init__.py
│   ├── access.py
│   ├── auth.py
│   ├── agents.py
│   ├── devices.py
│   ├── projects.py
│   ├── cases.py
│   ├── elements.py
│   ├── suites.py
│   ├── variables.py
│   ├── app_profiles/
│   │   ├── profiles.py
│   │   ├── releases.py
│   │   ├── overrides.py
│   │   ├── skip_rules.py
│   │   └── resolution.py
│   ├── executions.py
│   ├── execution_tree.py
│   ├── execution_queue.py
│   ├── reports.py
│   └── dashboard.py
└── services/
    ├── auth_service.py
    ├── agent_service.py
    ├── project_service.py
    ├── case_service.py
    ├── element_service.py
    ├── suite_service.py
    ├── variable_service.py
    ├── dashboard_service.py
    └── ws_ingest_service.py
```

依赖规则：

1. Repository 使用函数式接口，每个函数显式接收 `AsyncSession`，不保存全局 Session。
2. Repository 可以使用 `select/update/delete/insert`、`execute/get/scalar/scalars/add/add_all/delete/flush/refresh`，但禁止 `commit/rollback`。
3. Service 可以调用多个 Repository，并负责 `commit/rollback`；禁止在 Service 中构造 SQL 或调用 ORM 持久化方法。
4. API 和 `app/ws/handlers.py` 禁止直接调用 Session；只做参数解析、依赖注入、Service 调用和响应转换。
5. `app/ws/routes.py`、`worker_runtime.py`、`seed.py` 和 `scripts/` 可以创建 Session，但不能构造业务 SQL。
6. Repository 不抛 `HTTPException`；未找到返回 `None`，条件更新返回 `bool` 或受影响行数，唯一冲突由 `IntegrityError` 表达。
7. Service 将 Repository 结果转换为 `ApiError`、业务状态或响应 DTO。
8. Repository 初期允许返回 ORM 实体、标量、元组或明确的 dataclass；禁止依赖未显式加载的 lazy relationship。
9. 持久化对象字段赋值放在 Repository command 函数中；Service 只传入要变更的值和业务决策。
10. `repositories/__init__.py` 不批量 re-export，调用方从具体模块导入，避免循环依赖。

推荐函数形态：

```python
async def get_execution(db: AsyncSession, execution_id: int) -> Execution | None:
    return await db.get(Execution, execution_id)


async def create_execution(db: AsyncSession, values: dict) -> Execution:
    execution = Execution(**values)
    db.add(execution)
    await db.flush()
    return execution


async def try_lock_device(db: AsyncSession, device_id: int, execution_id: int) -> bool:
    result = await db.execute(
        update(Device)
        .where(Device.id == device_id, Device.status == "idle", Device.locked_by_execution.is_(None))
        .values(status="busy", locked_by_execution=execution_id)
    )
    return result.rowcount == 1
```

### 事务与副作用规则

| 场景 | 事务所有者 | 提交点 | 约束 |
|---|---|---|---|
| 纯查询 API | Service/请求 Session | 不显式提交 | 禁止为结束查询调用 `commit()` |
| 单资源写入 | Service | 完成校验、写入和审计后一次提交 | `IntegrityError` 后必须 rollback 再映射错误 |
| 多 Repository 写入 | Service | 全部写入成功后一次提交 | 中途失败不得留下部分数据 |
| 执行创建 | `execution_service` | Execution、快照、排除项、Queue 全部写入后提交 | revision 锁与快照必须在同一事务 |
| Worker 认领 | `worker_service` | 队列由 pending 变 claimed 后提交 | 保留 `FOR UPDATE SKIP LOCKED` |
| Worker 启动执行 | `worker_service` | 设备锁与 execution running 落库后提交 | 提交后才向 Agent 发送消息 |
| Worker 终态 | `worker_service` | 状态归并、报告、设备释放、queue done 一次提交 | 报告和设备释放不得部分成功 |
| Agent WS 消息 | `ws_ingest_service` | 单条消息落库后提交 | 提交成功后再广播或 ACK |
| 报告 HTML | `report_service` | 文件成功原子落盘后更新缓存元数据 | 不在事务中渲染模板或读取截图 |
| 清理任务 | `cleanup_service` | 一批文件处理完成后更新 DB | 单文件失败可记录并继续，DB 更新保持幂等 |

禁止在未提交事务中执行：

- `agent_manager.send()`；
- 内部 HTTP 请求；
- WebSocket broadcast/ACK；
- Appium/ADB 操作；
- 报告模板渲染和大文件读写；
- 可长时间阻塞的文件删除。

### 21.2 明确的事务阶段

`run_execution()` 拆成以下阶段，每个阶段使用独立短事务，任何网络等待都发生在事务外：

1. **认领事务**：`pending → claimed`，写入 `worker_id/claimed_at`，提交。
2. **启动事务**：重新读取 execution，CAS 锁定指定 device，execution 转 `running`，queue 保持 claimed，写启动日志，提交。
3. **载荷读取**：只读加载 Agent payload，Session 结束，不持有行锁。
4. **Agent 发送**：调用 `agent_sender(start_test)`；无数据库事务。
5. **发送失败补偿事务**：execution 转 error，进入统一 `_mark_terminal`，释放设备并完成 queue。
6. **终态轮询**：每轮使用新 Session 读取状态；不得复用认领时 Session。
7. **终态事务**：CAS 设置 `finalized_at`，归并残留子节点，upsert 报告，释放 device，queue 转 done，一次提交。

停止执行同样遵守：读取 `stopping` → 事务外发送 `stop_test` → 终态上报或超时后由统一终态事务收敛。

### 21.3 并发和幂等不变量

- `claim_next` 必须保留 `SELECT ... FOR UPDATE SKIP LOCKED`，并按创建时间稳定排序。
- `try_lock_for_execution` 必须使用单条条件 UPDATE：`status='idle' AND locked_by_execution IS NULL`。
- `try_finalize` 以 `finalized_at IS NULL` 为 CAS 条件；失败表示其他 Runtime 已完成，不重复写 Report。
- Report 按 `execution_id` upsert；重复终态不得新增第二行。
- `release_for_execution` 必须同时匹配 `locked_by_execution=execution_id`，不能释放其他任务的锁。
- queue done 必须匹配当前 execution；终态失败不得先把 queue 标 done。
- 独立 Worker 与 embedded Worker 仍不得同时启用扫描；本 Step 不改变 `WORKER_MODE`。

| `handle_case_status` | `execution_tree.update_case_status` | `record_case_status` |
| `handle_suite_status` | `execution_tree.update_suite_status` | `record_suite_status` |

| `handle_execution_result` | `executions.try_apply_agent_terminal`、`execution_tree`、`reports.get_by_execution` | `record_execution_result` |

`_find_snapshot_step`、`_parse_terminal_status`、`_merge_terminal_status`、`version_supported` 等纯函数保留，但建议移动到 `ws_protocol_service.py` 或 `ws_ingest_service.py`，`handlers.py` 最终只负责 payload 分派与广播。

### 22.3 单条消息处理协议

统一处理顺序：

```text
收到 payload
  → 创建短 Session
  → Service 校验 agent/execution/session_token
  → Repository 写入
  → Service commit
  → 关闭 Session
  → broadcast / execution_result_ack
```

失败规则：

- 校验失败或 commit 失败不得广播成功状态。
- `execution_result_ack` 只能在终态成功提交或确认既有幂等终态后发送。
- `step_result`、`assertion_result`、`case_status`、`suite_status` 的广播数据使用已提交结果。
- 重复 `execution_result` 必须再次 ACK，但不得重复新增日志、报告或修改已 finalized 的终态。
- 单条消息 Session 异常 rollback 后关闭，不影响同一 WS 后续合法消息。
- 断开连接后的 `mark_agent_offline` 使用全新 Session，不复用最后一条消息的失败 Session。

## 四、暂缓项

### Trace ID

当前执行链路已经完整透传 `execution_id` 和 `session_token`，优先应统一三侧结构化日志字段，而不是立即增加数据库列和协议字段。

只有出现以下需求时再立项 trace ID：

- 一个用户请求会创建多个 execution，单靠 execution_id 无法串联。
- 队列认领前的请求链路也需要跨服务追踪。
- 接入 OpenTelemetry、集中日志或 APM。

届时单独设计 HTTP `X-Request-ID`、Worker payload、Agent WS 和日志上下文，不与本轮结构重构混合。

## 五、每个 Step 的完成定义

每个 Step 必须同时满足：

1. 当前 Step 的业务子任务、测试和文档全部完成。
2. 不修改无关工作区文件，不带入 `.workbuddy/`、会话记录或未确认的根目录配置。
3. 后端涉及模型时必须审阅迁移并运行 `alembic check`。
4. 协议变更必须同步 Agent、后端、前端和权威架构文档。
5. 运行该 Step 涉及模块的完整门禁，不以针对性测试代替全量测试。
6. 门禁全部通过后只提交一次；失败、跳过和环境阻断必须如实记录。
7. 提交后 `git status --short` 只允许保留实施前已有的用户工作区内容。
8. Repository 不得出现 `commit/rollback`，Service 不得新增 SQL/ORM 持久化操作，API/WS handler 不得直接访问 Session。
9. 写操作必须有失败注入或并发测试证明事务边界；不能只验证成功路径。
10. 迁移前后的 REST 响应、WS payload、排序、分页、权限和状态机必须保持一致。
11. 每完成一个数据库重构 Step 必须同步缩减 `LEGACY_DB_ACCESS_ALLOWLIST`，不得把新文件加入白名单。
