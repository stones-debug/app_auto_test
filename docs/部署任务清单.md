# APP 自动化测试平台 — 部署任务清单

> 适用范围：将本平台从「开发环境」推进到「生产/测试环境可运行」所需完成的全部任务。
> 生成依据：`AGENTS.md`、`backend/.env(.example)`、`backend/app/core/config.py`、`backend/app/main.py`、`backend/worker.py`、`agent/config.yaml.example`、`docs/APP自动化测试平台_详细架构实施方案.md` §5 部署方案、`.github/workflows/ci.yml`。
> 当前状态（AGENTS.md 明示）：项目**尚在开发环境、未上线**，本清单按首次部署编排。

---

## 0. 部署前决策（必须先定，影响后续所有步骤）

- [ ] **确定部署形态**：单服务器一体部署（FastAPI 同时托管 API+静态前端） vs 分离部署（Nginx 反代 + FastAPI 仅 API + Agent 客户端）。
- [ ] **确定监听端口**：开发用 `8001`（本机 8000 已被 C-Lodop 占用）。生产环境需自选端口并在 `.env` / Nginx / 防火墙三处保持一致。⚠️ 架构文档 §5.2 的 Nginx 示例写的是 `8000`，与本仓库 `8001` 约定不一致，请统一。
- [ ] **Worker 模式**：`embedded`（默认，跟随 FastAPI 单进程启动，最省事） vs `external`（独立 `worker.py` 进程）。
- [ ] **WS 网关进程数（重要约束）**：架构文档 §10 明确 V1 的 WS 网关**必须单进程**运行（多 Uvicorn 进程会导致内部 WS 转发落错进程）。因此：
  - 若用 `embedded` 模式：直接单进程 `uvicorn`，不要开 Gunicorn 多 worker。
  - 若需横向扩展：跨进程广播需 Redis Pub/Sub（文档标注为 V2，当前未实现），V1 阶段请保持单进程。
  - ⚠️ 文档 §5.2 表格写「Gunicorn + Uvicorn 4-8 进程」与 §10 单进程约束**冲突**，V1 以单进程为准。
- [ ] **域名 / TLS**：生产强制 HTTPS/WSS（文档 §4.4）。确定对外域名、证书来源（自有证书 / ACME）。
- [ ] **数据库归属**：独立生产库（非开发库 `test_platform`），确定由 Docker、宿主机原生 PG，还是托管 RDS。

## 1. 密钥与配置（CR-21 安全基线，生产必做）

后端启动时 `validate_security_baseline()` 在 `ENVIRONMENT != development` 时**遇到以下任意弱配置会直接拒绝启动**：

- [ ] 复制 `backend/.env.example` → `backend/.env`（生产用，不提交真实密钥到仓库）。
- [ ] `ENVIRONMENT=production`。
- [ ] `JWT_SECRET_KEY`：随机长度 **≥32** 字符，禁用默认值。
- [ ] `INTERNAL_TOKEN`：随机且非默认值，长度 **≥32** 字符（用于 `/internal/*` 与 `/metrics` 鉴权）。
- [ ] `AGENT_USER_KEY_ENCRYPTION_KEY`：随机长度 **≥32** 字符（Windows 方案中用户 Key 可逆加密主密钥，生产必填）。
- [ ] `DATABASE_URL`：使用**强密码**的生产库地址，URL 中不得再含 `dev123`。
- [ ] `CORS_ORIGINS`：列出真实前端域名（如 `["https://test.example.com"]`）；**禁止 `*`**（与 `allow_credentials=True` 冲突）。
- [ ] 其余按需覆盖：`REPORTS_BASE_PATH`、`AGENT_RELEASES_PATH`、`MAX_UPLOAD_SIZE`、限流阈值、保留天数等。
- [ ] 校验：`ENVIRONMENT=production` 下启动一次，确认无 `部署安全基线未通过` 异常即配置过关。

## 2. 数据库

- [ ] 准备 PostgreSQL 实例（开发用 PG 18 原生，生产建议同版本或托管 RDS）。
- [ ] 建库与账号：创建生产库（如 `test_platform`），新建专用用户并设强密码；收回不必要权限。
- [ ] 配置自动备份（文档 §5.2 建议启用）。
- [ ] **执行迁移（不要 autogenerate）**：
  - 在 `backend/` 下：`uv run alembic upgrade head`
  - 校验：`uv run alembic check`（与 CI 一致）。
  - 注意：存在循环外键 `devices.locked_by_execution ↔ executions.device_id`，初始迁移已手工拆分，新迁移仍需注意建表顺序。
- [ ] **初始化种子账号**：`uv run python -m app.seed`（创建 `admin/admin123`，幂等）。
  - ⚠️ 部署后**立即修改 admin 密码**（当前为弱口令）。
- [ ] 确认 `WORKER_MODE` 对应实例能看到队列：迁移后消费端方可正常认领任务。

## 3. 后端服务部署

- [ ] 安装运行时：Python ≥3.11，`uv` 可用（本机需把 `%USERPROFILE%\.local\bin` 加入 PATH，否则 `uv run` 失败）。
- [ ] 安装依赖：`cd backend && uv sync --all-extras`。
- [ ] 准备 `backend/.env`（见第 1 节），确保 `REPORTS_BASE_PATH`、`AGENT_RELEASES_PATH` 指向的目录**已存在且可写**。
- [ ] 启动方式选择：
  - **单进程（V1 推荐）**：`uv run uvicorn app.main:app --host 0.0.0.0 --port <PORT> --ws-max-size <AGENT_WS_MAX_FRAME_BYTES>`（生产不要添加 `--reload`）。`--ws-max-size` 必须与 `AGENT_WS_MAX_FRAME_BYTES` 一致。
  - 或用自带脚本：`powershell -File start-backend.ps1 -Port <PORT> -NoReload`（脚本从应用配置读取 `AGENT_WS_MAX_FRAME_BYTES` 并传给 Uvicorn，会自动补 `.env`、可选 `-Migrate -Seed`）。
  - 直接绕过脚本启动 Uvicorn 时也必须显式配置 `--ws-max-size`；应用层检查仍保留作为纵深防御，不等同于网络入口帧限制。
- [ ] 静态前端托管（若采用一体部署）：`backend/app/main.py` 会自动挂载 `../frontend/dist`（若存在）。部署时把前端构建产物放到 `frontend/dist` 即可由同一端口提供页面+API+WS。
- [ ] **独立 Worker（仅当 `WORKER_MODE=external`）**：
  - `backend/.env` 设 `WORKER_MODE=external`。
  - 启动：`powershell -File start-worker.ps1`（或 `uv run python worker.py --worker-id worker-001 --enable-scans`）。
  - 多实例时**仅一个**带 `--enable-scans`（扫描/每日清理只跑一份）。
- [ ] 进程守护：用 systemd / Windows 服务 / 进程管理器保证崩溃自愈与开机自启。
- [ ] 验证：`GET /api/health` 返回 `{"status":"ok"}`。

---

## 4. 前端构建与托管

- [ ] 环境：Node ≥18.16（仓库锁 `<19`，勿用 Node 20+，否则 `vite`/部分依赖异常）。
- [ ] 安装依赖：`cd frontend && npm ci`（用 `package-lock.json` 保证一致）。
- [ ] **构建**：`npm run build`（= `vue-tsc -b && vite build`，含 TS 类型校验）。产物在 `frontend/dist/`。
  - 验证：`npm run test`（vitest）与 `npm run check:bundle`（包体预算）通过。
- [ ] 托管方式：
  - **A. Nginx 静态托管（推荐，性能更好）**：把 `frontend/dist` 部署到 Nginx root，配置 SPA 回退 `try_files $uri $uri/ /index.html`。
  - **B. FastAPI 一体托管**：把 `dist` 放到 `frontend/dist`，由后端 8001 端口直接 serve（见第 3 节）。
- [ ] 确认前端运行时代理目标与部署域名一致（开发用 `127.0.0.1:8001`，生产改为真实域名/WSS）。

---

## 5. 反向代理与 TLS（Nginx）

- [ ] 安装 Nginx（系统包管理器）。
- [ ] 配置 HTTPS（`listen 443 ssl http2`）、上传证书与私钥，启用 HSTS/Gzip。
- [ ] 路由：
  - `/` → 前端静态（`root .../dist; try_files ... /index.html`）。
  - `/api/` → 反代 FastAPI（注意 `proxy_read_timeout` 调大，如 300s，执行接口可能长耗时）。
  - `/ws/` → WebSocket 反代（`proxy_http_version 1.1` + `Upgrade`/`Connection "upgrade"`，`proxy_read_timeout 86400s`）。
  - 文档 §5.2 示例反代到 `127.0.0.1:8000`，请改成你实际后端端口。
- [ ] 强制 HTTP→HTTPS 跳转。
- [ ] 防火墙：仅对外暴露 443（与必要管理端口），后端端口不直连公网。

---

## 6. Agent 客户端部署（被测机 / 用户 Windows 机）

- [ ] **服务器地址**：Agent `config.yaml` 的 `server` 必须填 **`wss://` 生产地址**（不是 `ws://`，生产强制 TLS）；代码会校验地址合法性并拒绝内嵌凭据。
- [ ] **驱动模式**：`driver: mock`（联调）vs `driver: appium`（真实设备，需 `pip install 'agent[appium]'` 或安装包内置 Appium + ADB）。
  - 真机需配置 `appium_host`/`appium_port`、ADB 环境、USB/Wi-Fi 设备调试授权。
- [ ] **身份**：Agent 以本机 `install_id` 作 `agent_id`；绑定阶段只校验用户 Key，成功后下发机器 PSK 供 WS、上传和机器侧管理认证，无需在配置文件明文写 `agent_key`。
- [ ] **分发安装包**（Windows 方案 §3.4 / 文档 §5.3）：
  - 后端 `AGENT_RELEASES_PATH` 目录需放版本化安装包 + `latest.json`（`version/filename/sha256/size/published_at`）。
  - 提供 `GET /api/agent/releases/latest` 与下载令牌接口（前端下载入口依赖它）。
  - 构建链参考 CI `windows-agent-package`：self-check → PyInstaller → Inno Setup 安装包 → SHA256 manifest。
  - ⚠️ 安装包不入库、不打进前端 Bundle，由发布脚本复制到后端发布目录并原子更新 manifest。
- [ ] 终端用户：安装 → 登录自启 → 录入/绑定个人 Key（`/api/me/agent-key`）→ 连接设备 → 在前端选机执行。
- [ ] 升级：后端更新 `MIN_AGENT_VERSION` 提示旧版升级（当前为人工重装，无自动更新）。

## 7. 存储、清理与监控

- [ ] 报告/截图目录（`REPORTS_BASE_PATH`）挂在足够空间的磁盘（SSD/NAS），预留增长空间；文档 V3 阶段才考虑 MinIO/S3/OSS。
- [ ] 清理策略：Worker（embedded 模式下随 FastAPI 每日 3 点执行）按 `REPORT_RETENTION_DAYS`(90)/`SCREENSHOT_RETENTION_DAYS`(30)/`LOG_RETENTION_DAYS`(7) 清理；也可手动 `uv run python scripts/cleanup_reports.py --dry-run` 先预览。
- [ ] 监控：
  - `/metrics`：需内部令牌；Prometheus 在本机时才启用 `metrics_require_loopback=true`。远程采集必须使用网络白名单或反向代理鉴权，不能同时启用 loopback 并期待远程直连。
  - `/api/health` 接入存活探针。
  - 关注日志、执行队列堆积、Agent 离线、设备锁泄漏。

## 附：与文档不一致的已知冲突（部署时以本清单为准）

1. **端口**：AGENTS.md 开发用 `8001`，架构文档 §5.2 示例用 `8000` → 统一选一个并三处对齐。
2. **WS 多进程**：§5.2 写「Gunicorn 4-8 进程」，§10 明确 V1 必须单进程 → V1 单进程。
3. **Docker 化**：AGENTS.md 写「本机无 Docker、后端无 Docker 化要求」，架构 §5.1 给了 docker-compose 示例 → 按宿主实际选择，无需强制容器化。
4. **Worker 默认**：代码默认 `embedded`，文档 §5.1 dev 示例默认独立 `worker` 服务 → 生产建议 `embedded` 单进程最简。
