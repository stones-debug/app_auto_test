## 3. 详细发现

### RQ-01 [P1][确认问题] Agent 的 HTTP 基址解析只返回协议名

**证据**

- `agent/main.py:35-37` 将 `ws://host/path` 替换成 HTTP 后调用 `.split("/")[0]`。
- 对 `ws://127.0.0.1:8001/ws/agent` 的直接求值结果是 `http:`；WSS 输入结果是 `https:`。
- `agent/main.py:244-257` 将该结果同时传给 `BindingManager` 和 `Uploader`；`agent/main.py:352-353` 的命令行绑定也复用同一函数。
- 现有测试只覆盖 uploader 的 key 回调，没有覆盖 WebSocket URL 到 HTTP origin 的转换。

**影响**

用户绑定、绑定列表、解绑和截图上传都会构造类似 `http:/api/agent/...` 的无效地址。Mock 执行不截图时可通过，因此现有 78 个 Agent 测试没有发现问题。

**建议**

使用 `urllib.parse.urlsplit/urlunsplit`，只替换 scheme 并保留 `netloc`，明确丢弃 WS path、query 和 fragment。为 IPv6、端口、WSS、末尾斜杠和非法 URL 增加参数化测试。

**工作量**：S（约 0.5 天）。

**验证**：单元测试断言 `ws://127.0.0.1:8001/ws/agent → http://127.0.0.1:8001`，并用 mock HTTP server 覆盖 bind 与 upload 请求地址。

### RQ-02 [P1][确认问题] Appium 6 建连 API 使用错误，真实会话无法按 capability 启动

**证据**

- `agent/pyproject.toml:10` 的基础依赖固定为 `appium-python-client>=6.0.0`。
- `agent/executor/appium_driver.py:62-69` 调用 `appium_webdriver.Remote(self.command_executor, caps)`。
- 对已锁定的 Appium Client 6.0.0 动态检查得到签名：`Remote(command_executor, extensions=None, options=None, client_config=None)`；第二个位置参数是 `extensions`，不是 capabilities。
- `agent/tests/test_appium_smoke.py:20-48` 重复使用相同的错误调用，且默认被环境条件跳过。
- `agent/pyproject.toml:13-15` 又把 Appium 声明为可选依赖，和基础依赖重复且最低版本不同。

**影响**

真实模式会把 capability 字典绑定到 `extensions` 参数，不能按 UiAutomator2/XCUITest options 创建会话。现有 smoke test即使接入设备，也会先受到同一 API 错误影响。

**建议**

按平台创建 `UiAutomator2Options` 或 `XCUITestOptions`，通过 `options=` 传入；smoke test必须复用生产 `AppiumDriver`，避免测试代码复制错误调用。根据发行方式二选一：Appium 是 Windows Agent 必备依赖，或仅保留 `[appium]` extra，不要双重声明。

**兼容性**：会改变 Agent 内部 driver 构造方式，不改变后端协议；需明确只支持 Appium Client 6.x。

**工作量**：M（2～3 天，含 Android/iOS options 与 smoke test）。

**验证**：Mock options 单测 + 专用设备上完成建连、启动、定位、截图、停止、退出。

### RQ-03 [P1][确认问题] 三个“重试”入口均未满足后端 retry 契约

**证据**

- 后端 `backend/app/api/executions.py:383-400` 要求请求体包含 `device_id`，无 body 固定返回 `DEVICE_REQUIRED`。
- `frontend/src/api/executions.ts:148-150` 的 `retryExecution(id)` 不接受也不发送请求体。
- `frontend/src/views/Execution.vue:83-87` 和 `frontend/src/views/ExecutionDetail.vue:129-133` 直接调用该无 body API。
- `frontend/src/views/ReportDetail.vue:83-86` 把 execution ID 伪装成 `{kind: 'case', id: execId}`，会把执行 ID 当成用例 ID创建新执行。
- `frontend/src/composables/useRunFlow.ts:7-24` 只创建 `useDeviceSelect()` 状态，没有渲染 `DevicePicker`；默认设备不可用时没有可见选择弹窗。

**影响**

执行列表和执行详情的重试固定失败；报告详情可能运行错误用例、返回 404，或在默认设备不可用时没有后续交互。

**建议**

把 retry 定义为独立目标类型 `{kind: 'retry', executionId}`，由统一 DevicePicker 调用 `POST /executions/{id}/retry` 并发送 `{device_id, timeout_seconds?}`。列表、详情、报告三个入口只传 execution ID，不自行推导 case/suite。

**兼容性**：只调整前端 API 类型和调用链，后端公开接口无需变化。

**工作量**：M（1～2 天）。

**验证**：补充“默认设备直重试”“弹窗选设备”“设备冲突刷新”“case/suite/batch 重试”组件/API 测试。

### RQ-04 [P1][确认问题] 步骤参数契约漂移，继续执行和等待超时配置无效

**证据**

- 后端 `backend/app/schemas/case.py:114-128` 将 `continue_on_failure` 定义为 Step 顶层字段。
- Agent `agent/executor/test_runner.py:150-153` 却从 `step.params.continue_on_failure` 读取，因此顶层 true 永远不会生效。
- 前端 `frontend/src/api/cases.ts:4-10` 的 Step 类型没有 `continue_on_failure`，编辑器也没有对应控件。
- 前端为 click 提供 `wait_timeout`（`frontend/src/api/cases.ts:81-83`），后端也验证该参数，但 `agent/executor/actions.py:38-43` 没有传递它。
- `agent/executor/appium_driver.py:78-83` 虽声明 `wait_timeout`，实现仍直接调用一次 `find_element`。

**影响**

用户无法配置失败后继续；即使通过 API 手工写入，Runner 也会在失败步骤后中止。页面展示的等待秒数给出错误承诺，慢加载元素会立即失败。

**建议**

明确控制字段归属并保持三端一致：建议 `continue_on_failure` 保持 Step 顶层，Runner 直接读取顶层；前端补控件。`ExecutionContext.find_element` 接受 timeout，并由 click 等动作显式传递，Appium 实现使用 `WebDriverWait`。为动作/断言发布机器可读 manifest，减少三份手写元数据。

**兼容性**：保留现有 JSON wire shape即可无迁移修复；如移动字段则需兼容读取旧快照。

**工作量**：M（2～3 天）。

**验证**：失败步骤 `continue_on_failure=true/false` 双路径测试；延迟出现元素的 wait 成功/超时测试。

### RQ-05 [P1][确认问题] Agent 的 Appium 生命周期对异常和并发不安全

**证据**

- `agent/main.py:88-102` 用普通整数维护 `_appium_refs`，在 `await appium.start/wait_ready` 前后没有锁。
- `agent/main.py:111-119` 在进入 `try/finally` 之前执行 `_ensure_appium()`、`create_driver()` 和临时目录创建。
- `create_driver()` 抛错时不会发送 `execution_result=error`，也不会调用 `_release_appium()`；Worker 只能等待超时扫描。
- 多设备并发 start_test会创建多个 task（`agent/main.py:192-208`），因此两个任务可能同时观察到 refs 为 0 并重复启动 Appium。

**影响**

配置错误、驱动构造失败或临时目录异常可造成执行长期停留 running、Appium 引用泄漏；多设备并发时可能重复启停同一 Appium Server。

**建议**

用 `asyncio.Lock` 保护启动/引用计数/停止；把资源获取纳入最外层 try，并用布尔标记只释放已成功获取的资源。所有前置失败都尽力上报 error；清理异常只记录日志，不覆盖原始执行结果。

**工作量**：M（1～2 天）。

**验证**：并发两次 start、`create_driver` 抛错、wait_ready 失败、quit 失败和 stop 竞争测试。

### RQ-06 [P1][确认问题] 强制释放设备可让同一设备同时执行两项任务

**证据**

- `backend/app/api/agents.py:253-266` 的应急释放只把设备改为 idle 并清空 `locked_by_execution`。
- 关联 execution仍可能是 running，Agent 上的原执行任务也没有收到 stop。
- 新 Worker 的原子锁只检查设备当前为 idle 且无锁，因此释放后可立即把同一设备分配给另一执行。

**影响**

两项 Appium 会话可能争用同一 UDID，产生互相干扰、错误报告和难以复现的设备状态。Worker 的后续超时无法撤回已经启动的第二项任务。

**建议**

把“释放”定义为一个原子应急操作：锁定 Device 和关联 Execution，先将执行转 stopping/error 并触发 stop，完成终态汇总后才释放设备。若产品需要“仅清锁”，应要求确认并禁止关联执行仍为活动态。

**工作量**：M（2 天，含并发测试）。

**验证**：活动执行强制释放、Worker 同时认领、Agent 离线三种事务并发场景。

### RQ-07 [P1][确认问题] 有历史执行的 Agent 无法按当前端点完成删除

**证据**

- `backend/app/api/agents.py:92-102` 删除 Agent 前硬删除其全部 Device。
- `backend/app/models/execution.py:36` 的 `Execution.device_id` 指向 Device，没有 `ondelete` 行为。
- 初始迁移 `backend/alembic/versions/8d67e8abca27_init_all_tables.py:203-207` 同样创建了无 CASCADE/SET NULL 的外键。
- 现有 Agent 删除测试没有先创建引用设备的历史执行。

**影响**

一旦设备参与过执行，PostgreSQL 会拒绝删除 Device，管理端“注销 Agent”返回服务器错误。直接 CASCADE 又会破坏报告的历史设备引用。

**建议**

优先采用 Agent/Device 软注销，保留历史记录并禁止新任务；或者把 execution.device_id 改为 `ON DELETE SET NULL`，同时在执行快照中保存设备名称/UDID。API 在活动执行存在时应返回明确 409。

**兼容性**：软注销需要新增状态/时间字段；SET NULL 需要迁移和报告兼容。

**工作量**：M～L（3～5 天）。

**验证**：无执行、有终态执行、有活动执行、存在默认设备偏好四类删除场景。

### RQ-08 [P1][确认问题] 前端 CI 的 Node 版本与 Vitest 4 不兼容

**证据**

- `.github/workflows/ci.yml:76-85` 固定 Node 18 后执行 `npm test`。
- `frontend/package.json:29` 使用 Vitest `^4.1.11`。

**工作量**：S（0.5～1 天）。

**验证**：Node 18.16 下 `npm ci && npm test && npm run build`，并让 CI 使用完全相同的小版本。

### RQ-09 [P2][确认问题] 执行详情的 WebSocket 状态和路由参数不是响应式的

**证据**

- `frontend/src/views/ExecutionDetail.vue:23` 在 setup 时一次性计算 `executionId`。
- 同一 route record从 `/executions/1` 跳到 `/executions/2` 时 Vue Router会复用组件，但代码没有 watch route param。
- 页面自建 `connected`/`connecting`（`:28-29`），`subscribe()` 仅把 composable 返回值保存到 `socket`（`:84-116`），没有同步两组 ref。
- active execution期间 `connecting` 从未被设置为 false，因此 LiveLogViewer 会长期显示“连接中”。

**影响**

重试后跳转新执行详情仍可能继续请求旧 ID；连接指示不可信，socket 重新订阅时也缺少显式关闭旧连接的生命周期。

**建议**

把 route param做成 computed/watch，在变化时关闭旧 socket、清空状态并重新加载。直接使用 composable 暴露的 connected ref，并让其提供 connecting/error/retry 状态；订阅前保证旧 socket 已关闭。

**工作量**：S～M（1 天）。

**验证**：路由参数复用、连接/断开/重连、completed 后补拉和卸载清理组件测试。

### RQ-10 [P2][确认问题] 报告“只看失败”复选框会被处理函数再次反转

**证据**

- `frontend/src/views/ReportDetail.vue:137` 同时使用 `v-model="onlyFailed"` 和 `@change="toggleOnlyFailed"`。
- `toggleOnlyFailed()` 在 `frontend/src/views/ReportDetail.vue:56-59` 再次执行 `onlyFailed = !onlyFailed`。

**影响**

Element Plus 已通过 v-model 写入新值后，change handler把它翻回旧值，用户无法稳定启用过滤；展开索引也可能与过滤后的列表不同步。

**建议**

change handler接收新 boolean，只负责重算展开项，不再修改 v-model 本身；collapse item使用 case ID 而不是过滤后数组下标作为 name。

**工作量**：XS（小于 0.5 天）。

**验证**：失败/全部往返切换、过滤前后展开状态、零失败用例组件测试。

### RQ-11 [P2][确认问题] 日志分页和详情聚合存在查询/内存放大

**证据**

- `backend/app/services/execution_service.py:179-187` 为计算 total读取全部日志 ID 再 `len()`，每翻一页都会把匹配日志完整载入内存。
- `backend/app/api/executions.py:282-307` 对每个 ExecutionCase分别查询 steps 和 assertions，查询数约为 `1 + 2N`。
- `backend/app/services/report_service.py:48-71` 对报告详情重复同样的 N+1 模式。
- 报告详情还一次性返回全部日志（`report_service.py:110-140`），大型执行没有体积上限。

**影响**

长时间执行或大套件会使数据库往返、响应时间和 API 内存随用例/日志数量线性恶化，报告下载还会再次执行相同聚合。

**建议**

日志 total使用 `SELECT count(*)`；批量按 execution_case_id 查询 steps/assertions后在内存分组，或配置 ORM selectin loading。报告日志设置明确上限/分段策略，HTML 生成可流式或后台缓存。

**工作量**：M（2～3 天）。

**验证**：构造 100 case、10 万日志的查询计数和响应内存基准，断言详情查询数保持常数级。

### RQ-12 [P2][确认问题] 公共项目报告的列表与详情可见性仍不一致

**证据**

- 报告详情继续通过 `get_project_permission`，公开项目登录用户可读。
- `backend/app/api/reports.py:54-70` 未指定 project_id 时只选择 owner/member 项目，没有合并公开项目。
- 该行为与旧报告 CR-20 相同，也与“公开项目 viewer 可查看报告”的权限口径不一致。

**影响**

用户知道 report ID 或显式项目 ID 时可以访问，但报告中心默认列表无法发现同一资源，导致授权与检索体验分裂。

**建议**

抽取统一的“可见项目 ID”查询，供项目、执行、报告和仪表盘复用；若产品决定默认中心只展示“我的项目”，应在 API/页面命名和文档中明确，而不是形成隐式差异。

**工作量**：S（约 1 天）。

**验证**：owner/member/public-viewer/private-outsider 四角色的列表与详情矩阵测试。

### RQ-13 [P2][改进机会] 动作/断言协议仍由三端手工复制

**证据**

- 后端在 `backend/app/schemas/case.py` 维护 13 个动作和 8 个断言的参数模型。
- Agent 在 `agent/executor/actions.py`、`assertions.py` 维护 Registry 和执行逻辑。
- 前端在 `frontend/src/api/cases.ts` 再维护字段、默认值、是否需要元素和显示元数据。
- RQ-04 已经证明手工同步产生了真实行为漂移；Pydantic `ParamsBase.extra="ignore"` 还会静默丢弃未知参数。

**影响**

每次新增动作都必须跨三个包同步，编译和 Ruff 无法检查协议一致性；未知字段被忽略会把版本不兼容延迟到执行时暴露。

**建议**

由 Agent Registry 导出版本化 JSON manifest/OpenAPI extension，包含名称、参数 schema、默认值、元素需求和最小 Agent 版本。后端启动/CI 校验 manifest，前端由 manifest生成类型或表单元数据。新协议默认拒绝未知字段，兼容旧快照时显式做版本迁移。

**工作量**：L（约 1 个迭代）。

**验证**：CI 比较三端 manifest hash；新增一个动作只需修改单一来源并自动生成前后端契约测试。

### RQ-14 [P2][改进机会] 前端拆包有效，但图表和全量样式仍偏重

**证据**

- 构建最大 chunk约 515.80 kB / gzip 176.60 kB，来自仅工作台使用的 ECharts 模块集合。
- `frontend/src/main.ts:3` 全局导入 `element-plus/dist/index.css`，生成约 360.80 kB CSS。
- `frontend/vite.config.ts:28-39` 仅手工拆分 Vue/VueUse/draggable，并把警告阈值提高到 700 kB。

**影响**

首次进入工作台仍需下载较大图表 chunk；全站加载完整 Element Plus CSS。提高阈值隐藏了回归信号，没有建立实际体积预算。

**建议**

保持 ECharts 路由级加载并将其命名为独立 vendor chunk；评估更轻的 SVG/CSS 图表或延迟到图表进入视口再加载。启用 Element Plus 按需样式，并在 CI 对 gzip 后的路由 chunk/CSS 设置预算。

**工作量**：M（1～3 天）。

**验证**：构建清单快照、首屏资源总量预算、Dashboard 懒加载浏览器测试。

### RQ-15 [P3][改进机会] 高复杂度模块缺少静态类型和结构门禁

**证据**

- `worker_service.py` 约 565 行，同时承担变量、快照、队列、锁、终态和扫描任务。
- `CaseEditor.vue` 约 456 行，`executions.py` 约 401 行，`ws/handlers.py` 约 377 行，`agent/main.py` 约 367 行。
- Python 门禁只有 Ruff，没有 Pyright/mypy；协议和回调中大量使用裸 `dict`、`object`、未参数化 Callable。
- WS、Agent 生命周期和清理代码多处捕获宽泛 `Exception`；部分清理路径静默忽略异常。

**影响**

模块职责继续增长后，事务边界、异步取消和消息字段错误难以在评审阶段识别；当前多项 P1 都属于跨模块类型无法约束的问题。

**建议**

按职责拆分 Worker 的 snapshot/queue/finalizer/scanner，Agent 拆出 execution supervisor；为 WS payload使用 TypedDict/Pydantic model。先对新模块启用 Pyright basic，再逐步扩大范围。清理异常保留上下文日志和 execution ID。

**工作量**：L（分 2～3 个小 Step 渐进实施）。

**验证**：类型检查进入 CI，设置模块复杂度/文件尺寸趋势而非一次性大重构。

## 5. 改进路线

### 阶段 A：恢复核心闭环（建议作为下一个 Step）

1. 修复 RQ-01、RQ-02，并增加不依赖真实设备的 URL/options 单测。
2. 修复 RQ-03，统一三个重试入口和设备选择流程。
3. 修复 RQ-04，锁定步骤 JSON 契约并补 Runner 行为测试。
4. 将前端测试框架降到 Node 18 兼容版本，恢复 CI 一致性（RQ-08）。

### 阶段 B：设备与 Agent 生命周期

1. 为 Agent Appium 资源增加锁和异常安全清理（RQ-05）。
2. 重新定义强制释放事务语义（RQ-06）。
3. 引入 Agent/Device 软注销或设备快照，解决历史 FK（RQ-07）。

### 阶段 C：前端正确性与性能

1. 修复执行详情响应式 socket/route 生命周期和报告过滤（RQ-09、RQ-10）。
2. 把详情聚合改成常数级查询并优化日志 count/上限（RQ-11）。
3. 统一公共项目可见查询（RQ-12），建立 bundle 预算（RQ-14）。

### 阶段 D：降低长期变更成本

1. 建立版本化 Action/Assertion manifest，逐步替代三端手写契约（RQ-13）。
2. 拆分 Worker/Agent supervisor，逐步引入 Pyright 与结构门禁（RQ-15）。
3. 在独立测试库补跑后端全量 pytest、Alembic 漂移检查和多 Worker 并发终态测试。

## 6. 建议的发布门槛

- Node 18.16、Python 3.11、PostgreSQL 独立测试库上的全部 CI 门禁通过。
