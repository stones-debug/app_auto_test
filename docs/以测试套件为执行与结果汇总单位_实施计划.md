# 以测试套件为执行与结果汇总单位的实施计划

> 版本 v1.0 ｜ 日期 2026-08-26 ｜ 状态：待执行
> 本文档为实施唯一权威口径；与代码/其它文档冲突时以本文档为准。

## 1. 总体设计

执行结构由当前的扁平用例列表调整为：

```text
Execution
└── ExecutionSuite
    ├── 套件前置步骤
    ├── ExecutionCase
    │   ├── 用例前置步骤
    │   ├── 用例主步骤
    │   ├── 断言
    │   └── 用例后置步骤
    └── 套件后置步骤
```

### 1.1 核心执行规则

- 批量运行仍创建一条 `Execution`，一次锁定设备并复用同一个 Appium Session。
- 按用户提交的套件顺序串行执行，套件内按 `sort_order` 执行用例。
- 同一用例属于多个套件时，在每个套件中分别执行并生成独立结果。
- 单用例入口继续保留：
  - 从具体套件上下文发起时，使用该套件作为执行容器。
  - 无套件上下文时，包装为“单用例执行”虚拟套件。
- 一个套件或用例失败后继续执行后续套件。
- 套件前置失败时：
  - 当前套件所有用例标记为 `skipped`。
  - 仍执行套件后置。
  - 当前套件判定为 `failed`，继续下一套件。
- 套件后置失败时当前套件判定为 `failed`，不影响后续套件。
- 用户主动停止时不再执行尚未开始的套件后置操作，当前节点标记为 `stopped`，其余节点收敛为 `skipped`。
- 套件前后置仅支持 Action Registry 操作，不支持断言。
- 套件前后置始终执行，不受现有“用例前置/后置”运行开关影响。
- APP 档案可以跳过或覆盖套件前后置中的单个步骤。
- N/A 内容不进入实际执行树，在独立区域按套件→用例→步骤/断言分组展示。

## 2. 数据模型、解析器与接口

### 2.1 数据模型

新增 `execution_suites`：

- `id`
- `execution_id`
- `suite_id`，虚拟套件时为空
- `suite_name`
- `suite_order`
- `is_virtual`
- `status`
- `setup_steps_snapshot`
- `teardown_steps_snapshot`
- `elements_snapshot`
- `started_at`、`finished_at`、`duration`
- `error_message`
- 唯一约束：`(execution_id, suite_order)`
- 非虚拟套件唯一约束：`(execution_id, suite_id) WHERE suite_id IS NOT NULL`

调整 `execution_cases`：

- 新增非空 `execution_suite_id` 和 `case_order`。
- 移除执行内按原始 `case_id` 唯一的约束。
- 改为 `(execution_suite_id, case_id)` 和 `(execution_suite_id, case_order)` 唯一。
- 相同 `case_id` 可以在不同 `execution_suite_id` 下出现。

调整 `execution_steps`：

- 支持两种互斥父节点：
  - 套件步骤：`execution_suite_id` 有值，`execution_case_id` 为空。
  - 用例步骤：`execution_case_id` 有值，`execution_suite_id` 为空。
- 增加明确阶段：
  - `suite_setup`
  - `case_setup`
  - `case_main`
  - `case_teardown`
  - `suite_teardown`
- 用检查约束保证父节点与阶段一致。
- 分别建立套件阶段顺序、用例顺序的部分唯一索引。

调整 `execution_assertions`：

- 改为直接关联 `execution_case_id`。
- 增加 `assertion_order`。
- 创建执行快照时预建 pending 断言，Agent 使用 `execution_assertion_id` 上报结果。

调整 `test_suites`：

- 新增 `setup_steps JSON/JSONB NOT NULL DEFAULT []`。
- 新增 `teardown_steps JSON/JSONB NOT NULL DEFAULT []`。
- 步骤结构复用现有 Action Step，必须包含稳定 UUID `key`、`order`、`action`、`params`、`continue_on_failure`。
- 后端统一生成或校验 UUID，并通过 Action Registry 校验参数。

扩展报告统计字段：

- 现有 `total/passed/failed/error_count/skipped/success_rate` 保持为用例统计和主要成功率。
- 新增套件统计与成功率。
- 新增步骤统计与成功率。
- 步骤统计包含套件步骤和用例步骤，断言继续单独展示。
- 成功率分母均为 `passed + failed + error`，不包含 skipped 和 N/A。

### 2.2 开发环境迁移

项目尚未上线，不实现旧执行数据兼容：

- 迁移前解除设备的执行锁并恢复可用状态。
- 清理所有执行、队列、报告、日志、截图元数据和执行排除记录。
- 重建执行相关约束和层级。
- 保留测试套件、用例及已有套件成员关系。
- 套件前后置初始化为空数组。
- 删除无法确定套件上下文的旧节点覆盖记录；已有套件级跳过规则可保留。
- 不增加双读、兼容字段或旧 Agent 协议分支。

### 2.3 配置解析器

解析结果改为：

```text
ResolvedExecution
└── suites[]
    ├── suite snapshot
    ├── setup_steps[]
    ├── cases[]
    │   ├── case snapshot
    │   ├── steps[]
    │   └── assertions[]
    └── teardown_steps[]
```

解析规则：

- 严格保留请求中的套件顺序及套件内用例顺序。
- 不再对跨套件共享用例去重。
- 所有跳过、变量和节点覆盖均以 `suite_id` 作为上下文解析。
- 套件前后置变量使用全局、项目、套件、APP 档案和执行参数，不使用用例级变量。
- 套件前后置使用到的元素固化到 `ExecutionSuite.elements_snapshot`。
- APP 档案规则增加 `suite_step` 目标类型：
  - 套件步骤：必须有 `suite_id + node_key`，不得有 `case_id`。
  - 用例步骤/断言：必须有 `suite_id + case_id + node_key`。
- 节点覆盖表补充 `suite_id`，避免共享用例在不同套件中的覆盖互相污染。
- 一个套件所有用例均被排除时，不创建实际 `ExecutionSuite`，整体放入 N/A 区，不执行其前后置。
- 预检统计增加可执行套件、套件步骤、用例实例、用例步骤及各层 N/A 数量。

### 2.4 REST API

扩展现有套件接口：

- `POST /api/projects/{project_id}/suites`
- `PUT /api/suites/{suite_id}`
- `GET /api/suites/{suite_id}`

增加字段：

```json
{
  "setup_steps": [],
  "teardown_steps": []
}
```

单用例创建及预检增加可选字段：

```json
{
  "context_suite_id": 123
}
```

校验规则：

- 仅单用例运行允许提交。
- 用例必须确实属于该套件。
- 套件、用例、项目和 APP 档案必须属于同一项目。
- 未提供时创建虚拟套件，且不应用任何套件专属变量或规则。

执行详情由 `cases` 改为：

```json
{
  "suites": [
    {
      "id": 1,
      "suite_id": 10,
      "suite_name": "登录回归",
      "suite_order": 1,
      "status": "passed",
      "setup_steps": [],
      "cases": [],
      "teardown_steps": []
    }
  ]
}
```

报告详情增加：

- `report.suites`
- `report.cases`
- `report.steps`
- `suites`
- `not_applicable_suites`

不保留旧扁平 `cases` 响应兼容。

## 3. Agent 协议与执行引擎

### 3.1 协议升级

将协议版本提升到 `2.0.0`，重新生成后端和前端 Registry 产物。旧版 Agent 不允许领取新执行，Windows Agent 安装包与后端同步发布。

`start_test` 改为：

```json
{
  "type": "start_test",
  "execution_id": 100,
  "suites": [
    {
      "execution_suite_id": 1001,
      "suite_id": 20,
      "suite_name": "基础功能",
      "suite_order": 1,
      "setup_steps": [
        {
          "execution_step_id": 5001,
          "action": "launch_app",
          "order": 1,
          "params": {}
        }
      ],
      "cases": [
        {
          "execution_case_id": 2001,
          "case_id": 30,
          "case_order": 1,
          "steps_snapshot": [],
          "assertions_snapshot": []
        }
      ],
      "teardown_steps": []
    }
  ]
}
```

Agent 上报增加或调整：

- `suite_status`：按 `execution_suite_id` 上报 running/终态。
- `case_status`：按 `execution_case_id` 上报 running/终态。
- `step_result`：按 `execution_step_id` 上报。
- `assertion_result`：每项携带 `execution_assertion_id`。
- `log`：可选携带套件、用例和步骤快照 ID。
- `execution_result`：仍作为整次执行结束信号。

后端必须校验所有快照 ID 属于当前 execution、Agent、设备和 session token，禁止仅按原始 `case_id + step_order` 更新结果。

### 3.2 Agent 执行顺序

```text
创建一次 Driver/Appium Session
for suite:
    suite_status(running)
    执行 suite_setup
    if suite_setup 失败:
        套件内用例全部 skipped
    else:
        for case:
            case_status(running)
            用例前置
            用例主步骤
            用例断言
            用例后置
            case_status(terminal)
    执行 suite_teardown
    汇总 suite_status
汇总 execution_result
关闭 Session
```

补充规则：

- `continue_on_failure=true` 只表示继续执行当前阶段剩余步骤，已发生的失败仍会使该阶段失败。
- 套件前置失败后，跳过用例，但继续执行套件后置。
- 套件状态优先级为：`error > failed > stopped > skipped > passed`。
- Worker/后端最终汇总以数据库实际子节点状态为权威，不允许 Agent 的 passed 覆盖已落库的失败。
- 停止、断线和超时时，在唯一终态事务中收敛未完成的套件、用例、步骤和断言。
- 重试仅允许 `passed/failed/error/stopped/cancelled` 终态；在同一事务内克隆原执行已经物化的套件、
  用例、步骤、断言、节点和不适用项快照，重新映射全部父 ID 后入队，不读取当前资产或 APP 档案。
  快照不完整返回 `EXECUTION_SNAPSHOT_NOT_READY` 且回滚；历史报告始终读取旧快照。

## 4. 前端与报告改造

### 4.1 套件编辑页

在套件基本信息和用例列表中增加：

- “套件前置步骤”折叠编辑区。
- “套件后置步骤”折叠编辑区。
- 复用现有 `CaseStepEditor` 的 Action 编辑能力。
- 支持新增、复制、删除、排序、收起和展开。
- 禁止添加断言。
- 保存时与套件元数据一并更新并递增项目测试资产 revision。
- 未保存离开页面时继续使用现有离开确认机制。

### 4.2 APP 档案工作台

套件树结构调整为：

```text
套件
├── 套件前置
│   └── 操作步骤
├── 用例
│   ├── 用例步骤
│   └── 断言
└── 套件后置
    └── 操作步骤
```

套件步骤支持：

- 设置/取消跳过。
- 填写跳过原因。
- 参数覆盖。
- “只看跳过项”和“只看覆盖项”筛选。
- 显示正常、跳过、继承跳过和覆盖标签。

### 4.3 执行详情与实时更新

执行时间线按套件卡片展示：

- 套件摘要显示状态、用例通过数、步骤通过数和耗时。
- 展开后依次显示套件前置、用例列表、套件后置。
- 用例可继续折叠，展开后显示步骤和断言。
- 实时更新使用 `execution_suite_id`、`execution_case_id`、`execution_step_id`，不再使用原始 `case_id` 查找节点。
- 执行失败时自动展开第一个失败套件及失败用例。
- 用户停止后正确显示 stopped/skipped 状态。

### 4.4 报告页面

顶部统计分为：

- 主要指标：用例成功率。
- 套件：总数、通过、失败、异常、跳过、成功率。
- 用例：总数、通过、失败、异常、跳过、成功率。
- 步骤：总数、通过、失败、异常、跳过、成功率。
- N/A：不参与任何成功率。

报告正文按照套件→用例→步骤展示，套件前后置直接展示在套件节点下；断言保留在对应用例下。

N/A 使用独立折叠区域，按套件→用例→步骤/断言组织，不混入实际执行状态。

HTML 下载报告与页面报告使用同一套层级聚合数据，避免两套统计口径。

### Step 5：全链路验收

必须覆盖：

1. 两个套件引用同一用例时，该用例执行两次且结果完全隔离。
2. 同一共享用例在两个套件中应用不同变量、跳过和节点覆盖。
3. 套件和用例严格按配置顺序执行。
4. 套件前置失败后用例全部 skipped，套件后置仍执行，后续套件继续。
5. 套件后置失败导致套件失败但不阻断后续套件。
6. 用例失败后继续执行当前套件及后续套件。
7. 单用例无上下文时生成虚拟套件；有上下文时使用指定套件规则。
8. 用户停止、Agent 断线和执行超时后所有节点状态正确收敛。
9. APP 档案可单独跳过和覆盖套件前后置步骤。
10. 所有用例均为 N/A 的套件不执行前后置，只进入 N/A 区。
11. 实时消息不会因共享 `case_id` 更新到错误套件。
12. 套件、用例、步骤成功率与数据库终态完全一致。
13. 历史报告只读取执行快照，不受之后修改套件影响。
14. Driver/Appium Session 在多套件执行过程中只创建和销毁一次。
15. 完成 Backend、Agent、Frontend 全量门禁及 Windows Agent `--self-check`。

## 默认假设

- 套件是调度、状态汇总和报告展示单位，但整次批量运行仍共用一台设备和一个 Session。
- 套件本身不嵌套其他套件。
- 同一个批量请求中的 `suite_ids` 必须去重，并保留首次出现顺序。
- 套件运行时失败不会触发自动重试或自动切换设备。
- 用例断言保持在用例层，不允许添加套件级断言。
- 套件运行时 skipped 与 APP 档案 N/A 含义不同，二者不得合并统计。
- 当前为开发环境，可清理历史执行数据，并直接停用协议 1.0，不建设兼容层。
