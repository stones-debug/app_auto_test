# APP 自动化测试平台代码审查报告

> 审查日期：2026-08-21  
> 审查范围：`backend/`、`agent/`、`frontend/`、数据库迁移、运行脚本及当前 UI 预览辅助文件  
> 权威基线：`docs/APP自动化测试平台_详细架构实施方案.md` V1.1，第 10 章优先  
> 审查方式：静态代码审查、架构对照、权限与数据流分析、自动化测试、Lint、前端生产构建、Alembic 漂移检查  
> 说明：本报告只记录问题与建议，未修改现有业务代码。

## 1. 结论摘要

项目已经形成可运行的 V1 主体：FastAPI、Worker、独立 Agent 和 Vue 前端的职责边界基本符合 V1.1 架构，正常路径测试、Lint 和前端类型构建均通过。

但当前版本不建议直接部署到多人共享或生产环境。核心原因不是代码风格，而是权限边界、Agent 信任边界、停止机制、截图链路和真实 Appium 接线仍存在高风险缺口。本次共记录：

| 等级 | 数量 | 含义 |
|---|---:|---|
| P0 / 严重 | 1 | 可形成服务器本地文件读取链，应立即处理 |
| P1 / 高 | 12 | 权限绕过、核心功能失效、执行或报告错误 |
| P2 / 中 | 11 | 数据一致性、会话、筛选、重连和部署加固问题 |
| P3 / 低 | 2 | 易用性、缓存恢复与维护性问题 |

最优先的四项工作是：

1. 切断 `Agent step_result.screenshot_path → 报告生成器本地文件读取` 链路。
2. 补齐变量、执行控制、Agent/设备管理的授权模型，并停止向列表接口返回 Agent PSK。
3. 将 Agent 执行改为后台任务，使接收循环可以实时处理 `stop_test`，同时为 `stopping` 增加超时兜底。
4. 接通截图 HTTP 上传并补齐真实 Appium 的 host、port、UDID、platformName、automationName 等能力配置。

## 3. 架构评价

### 3.1 已做得较好的部分

- FastAPI 负责 REST、WS 网关、执行明细落库和广播；Worker 负责排队、设备锁与终态汇总；Agent 负责动作和断言执行，主职责划分与 V1.1 第 10 章一致。
- Worker 使用 `FOR UPDATE SKIP LOCKED` 认领队列，并用条件更新原子抢占设备，方向正确。
- 项目、用例、元素、套件的常规接口大多使用统一项目权限依赖。
- 报告附件代理使用 `resolve()` 和 `is_relative_to()` 防止 URL 文件访问路径穿越。
- JWT 区分 access/refresh，并为 refresh token 加入 `jti`、哈希存储与撤销记录。
- SQL 查询均使用 SQLAlchemy 表达式，没有发现直接拼接用户输入形成 SQL 注入的代码。
- 后端测试按约定处理 asyncpg 事件循环与数据清理，当前测试可重复执行。

### 3.2 主要结构性缺口

- 系统没有“平台管理员”字段或依赖，但设备/Agent 和全局变量是平台级资源。
- Agent 只通过 PSK 证明“它是某个 Agent”，后续消息没有证明“它正在执行该 execution”。
- 数据库状态机分散在 API、Worker 扫描和 WS handler 中，缺少统一的原子状态转换函数。
- 用例的 `steps/assertions` 只验证为任意字典，前后端与 Agent Registry 之间没有共享的严格契约。
- Mock 路径较完整，真实 Appium、截图上传和停止并发路径尚未形成闭环。

## 4. 详细问题

### 4.1 P0 / 严重

#### CR-01：可通过伪造 screenshot_path 读取服务器本地文件

**证据**

- `backend/app/ws/handlers.py:117-173` 直接信任 Agent 回传的 `screenshot_path` 并写入数据库。
- `backend/app/services/report_service.py:144-148` 只按第一个 `/` 截断路径，没有做路径归一化或目录约束。
- `backend/app/services/report_service.py:151-163` 将该路径与报告目录拼接后直接 `read_bytes()`，没有使用 `is_relative_to()`。
- `backend/app/templates/reports/report.html:93` 把读取内容以 base64 写入可下载 HTML。
- Windows 下 `Path(base) / Path('C:\\Windows\\win.ini')` 会得到绝对路径 `C:\\Windows\\win.ini`，不会留在报告目录内。
- `backend/app/api/agents.py:31-48` 和 `backend/app/schemas/agent.py:11-24` 又会把 Agent ID 与 PSK 返回给任意登录用户，降低了利用门槛。

**影响**

任意登录用户可创建或冒充 Agent，向自己可访问的执行注入 Windows 绝对路径或 UNC 路径，随后下载报告并从 HTML 源中提取服务器可读文件的 base64 内容。这可能泄露 `.env`、配置文件、密钥或操作系统文件。

**建议**

1. 数据库只保存上传接口返回的服务端对象 ID/相对对象键，禁止 WS 自由提交文件系统路径。
2. 报告生成前执行 `target = (execution_dir / relative_path).resolve()`，并强制 `target.is_relative_to(execution_dir.resolve())`。
3. 拒绝绝对路径、盘符、UNC、反斜杠、`..` 和非预期目录前缀。
4. 上传成功后由服务端把对象与 `execution_id`、`execution_step_id`、`agent_id` 绑定。
5. Agent PSK 只在创建时返回一次，列表接口一律脱敏。

**必须增加的测试**

- `C:\\Windows\\win.ini`、`\\\\server\\share\\x`、`../x`、混合分隔符路径均被拒绝。
- Agent A 不能给 Agent B 的执行写截图。
- 报告生成器只能读取 `execution_<id>/screenshots/` 内文件。

### 4.2 P1 / 高

#### CR-02：变量接口没有项目权限校验，可跨项目读取、修改并污染全局执行

**证据**

- `backend/app/api/variables.py:24-100` 的四个端点只要求登录，没有调用 `get_project_permission` 或角色依赖。
- `list_variables` 在 `project_id` 缺失时可以返回同一 scope 的全部变量。
- `create_variable` 不验证 scope 与 project/suite/case 的归属关系。
- `frontend/src/views/Variable.vue:45-54` 创建全局变量时仍携带当前 `project_id`。
- `backend/app/services/worker_service.py:64-73` 读取全局变量时只检查 `scope == 'global'`，忽略 `project_id`。

**影响**

任意登录用户，包括公开项目 viewer，可读取其他项目变量、修改或删除变量，并创建影响所有项目执行的“全局变量”。这既是数据泄露，也是执行参数投毒。

**建议**

- project/suite/case scope 必须反查所属项目并校验 viewer 只读、member 以上可写。
- global scope 仅平台管理员可写；普通用户是否可读需明确产品规则。
- 使用 Pydantic model validator 和数据库 CHECK 约束保证 scope 与外键组合合法。
- 为作用域内名称增加数据库唯一约束，处理并发创建冲突。

#### CR-03：Agent/设备管理对任意登录用户开放，并在列表中长期暴露 PSK

**证据**

- `backend/app/api/agents.py:31-153` 的查询、创建、删除、强制释放均只依赖 `get_current_user`。
- `backend/app/schemas/agent.py:11-24` 的 `AgentOut` 始终包含 `agent_key`。
- `frontend/src/api/agents.ts:5-16` 和 `frontend/src/views/Device.vue:46` 直接消费并展示该密钥。
- 设计文档权限矩阵规定 Agent/设备管理不属于普通 member/viewer。

**影响**

任何账号都能读取全部 Agent 密钥、注册/注销 Agent、删除设备、强制释放正在执行的设备锁。攻击者可冒充 Agent 或破坏所有执行任务。

**建议**

- 增加平台管理员或明确的设备池授权模型。
- 拆分 `AgentCreateResponse` 与 `AgentListItem`；PSK 只创建时显示一次。
- 数据库存储 PSK 哈希；支持轮换和吊销。
- 强制释放设备时同步、原子地处理关联 execution，而不是只清空设备锁。

#### CR-04：公共项目 viewer 可以创建、停止和重试执行

**证据**

- `backend/app/api/deps.py:67-68` 把公共项目非成员解析为 `viewer`。
- `backend/app/api/executions.py:57-110` 创建执行时只调用 `get_project_permission`，没有检查 owner/admin/member。
- `backend/app/api/executions.py:206-227` 停止和重试同样只检查“可访问”。
- 权威权限矩阵规定公开项目其他登录用户不能执行测试。

**影响**

viewer 可消耗公共设备、制造执行队列、停止其他人的任务并反复重试，形成越权与资源消耗攻击。

**建议**

创建、停止、重试统一要求 `owner/admin/member`；报告和执行详情可继续按产品规则对 viewer 只读开放。停止操作还应考虑只有创建者或 admin/owner 可执行。

#### CR-05：Agent 回传没有绑定当前 Agent、设备和执行，可篡改任意执行

**证据**

- `backend/app/ws/routes.py:111-122` 只要 WS 已注册，就把消息交给 handler。
- `backend/app/ws/handlers.py:93-279` 的 `agent_id` 参数没有用于验证 execution 的 `device_id → agent_id`。
- `handle_log`、`handle_step_result`、`handle_assertion_result`、`handle_execution_result` 都接受消息中的任意 `execution_id`。
- `backend/app/api/agent.py:28-58` 上传接口也未验证 execution 是否分配给当前 Agent。

**影响**

任意有效或被攻陷 Agent 可以伪造其他项目的日志、步骤、断言和终态，破坏测试可信度；结合 CR-03，普通登录用户也可取得所需 PSK。

**建议**

- 每条消息都加载 execution、device，验证 `execution.device_id == device.id`、`device.agent_id == current_agent_id`。
- 只允许 `running/stopping` 执行接收结果，并通过原子状态转换防止终态反写。
- `start_test` 生成一次性 execution session token，Agent 回传与上传均携带并校验该 token。
- 对消息建立严格 Pydantic schema，非法消息返回协议错误而不是静默忽略或破坏 DB session。

#### CR-06：停止机制端到端失效，`stopping` 还可能永久卡住

**证据**

- `agent/ws_client.py:94-108` 在接收循环中直接 `await self.on_message(message)`。
- `agent/main.py:96-102` 收到 `start_test` 后直接等待整个 `run_execution`，执行完成前无法继续读取 `stop_test`。
- `backend/app/services/worker_service.py:407-416` 遇到 `stopping` 会循环发送停止消息，但没有截止时间。
- `backend/app/services/worker_service.py:449-459` 超时扫描只检查 `running`。
- `backend/app/services/worker_service.py:478-481` Agent 失联也只终结 `running`，不处理 `stopping`。

**影响**

正常情况下停止消息要等执行结束后才会被 Agent 读取，用户停止无效；动作阻塞或 Agent 失联时 execution 可永久停留在 `stopping`，Worker 任务也永久占用。

**建议**

- Agent 接收循环只负责分发，`start_test` 使用独立 task；保存 `execution_id → task/cancel_event/driver`。
- `stop_test` 立即设置对应事件并尝试终止 Appium session。
- Worker 对 `running` 与 `stopping` 使用统一 deadline；停止宽限期后强制 `stopped/error` 并释放设备。
- 状态转换必须原子化并禁止终态被晚到消息覆盖。

#### CR-07：截图 HTTP 上传器未接线，正常执行会保存 Agent 本地路径

**证据**

- `agent/main.py:10,45` 只导入并声明 `Uploader`，没有实例化或调用。
- 全仓库 `upload_screenshot` 仅在 `agent/uploader.py` 中定义，没有调用方。
- `agent/executor/test_runner.py:102-110` 把动作返回的本地路径直接放入 `step_result`。
- `backend/app/ws/handlers.py:164,173` 把本地路径直接存入服务端数据库。

**影响**

Agent 和 FastAPI 不在同一文件系统时，报告截图必然无法显示；同时本地路径进入服务端又形成 CR-01 的输入来源。

**建议**

Runner 完成截图后立即调用 uploader，成功后只回传服务端对象键；上传失败应记录明确错误，不能把 Agent 本地路径当作服务端路径。

#### CR-08：真实 Appium 模式未使用配置或目标设备能力，主路径尚不可交付

**证据**

- `agent/config.yaml.example:9-10` 定义了 `appium_host/appium_port`。
- `agent/main.py:51-52` 只将字符串 mode 传给 `create_driver`。
- `agent/executor/driver.py:126-130` 始终创建默认 `AppiumDriver()`，忽略 host、port、设备和 capabilities。
- `agent/executor/appium_driver.py:20-33` 只设置 appPackage、appActivity、noReset，没有 UDID、platformName、automationName。
- Worker 虽在 `start_test.device` 中下发 UDID/platform，Agent `run_execution` 没有使用该字段。
- 当前 Agent 测试没有真实 Appium smoke test。

**影响**

即使安装 Appium 依赖并连接真机，也无法可靠地为 Worker 选中的设备建立正确 session，多设备环境尤其会选错或无法启动。

**建议**

- 用 Worker 下发的设备信息构造 UiAutomator2/XCUITest options。
- 将 config 的 host/port、通用 capabilities、命令超时传入 driver。
- 对 Android/iOS 分别提供受支持 locator/action 实现和 smoke test。
- 在 CI 或专用测试机增加最小真实会话：建连、launch、find、screenshot、quit。

#### CR-09：用例创建路由和编辑器参数模型使多数动作/断言无法配置

**证据**

- `frontend/src/views/Case.vue:53-55` 新建按钮跳到 `/cases/new`。
- `frontend/src/router/index.ts:40-43` 只声明 `/cases/:caseId/edit`，因此 `/cases/new` 会命中兜底并跳回项目列表。
- `frontend/src/views/CaseEditor.vue:180-183` 所有动作只有 `params.value` 一个输入框。
- Agent 动作实际需要 package/activity/no_reset、direction/duration、filename、attribute/variable_name、x/y 等不同字段。
- `frontend/src/views/CaseEditor.vue:211-218` 对 `element_exists` 隐藏元素选择器；`regex_match` 写 `expected`，Agent 却读取 `pattern`。
- `backend/app/schemas/case.py:7-24` 仅把步骤和断言验证为任意字典，无法在 API 层阻止错误结构。

**影响**

UI 无法新建用例；即使修正路由，launch_app、sleep、swipe、screenshot、tap_coordinate、get_attribute、regex_match、element_exists 等多数 Registry 项仍无法正确配置，真实执行会失败或产生假阳性。

**建议**

- 修正新建路由并增加路由单元/E2E 测试。
- 以 Registry 元数据驱动动态表单，每个动作/断言定义字段、类型、必填、范围与默认值。
- 后端建立 discriminated union schema，按 `action/type` 严格校验嵌套参数。
- 前端提交前和后端入库前均校验 element_id 与项目归属。

#### CR-10：报告成功率数据库类型与权威设计不一致

**证据**

- 权威设计文档 `reports.success_rate` 为 `DECIMAL(5,2)`。
- `backend/app/models/execution.py:106` 把 `Mapped[float]` 映射为 `Integer`。
- 初始迁移 `backend/alembic/versions/8d67e8abca27_init_all_tables.py:312` 同样创建为 Integer。
- `backend/app/services/worker_service.py:317` 实际会生成如 `66.67` 的小数。

**影响**

数据库无法按设计保存两位小数；asyncpg 的整数参数绑定可能直接拒绝 float，或者至少造成精度丢失。现有测试只覆盖整数成功率，没有暴露问题。

**建议**

新增迁移改为 `Numeric(5, 2)`，ORM 使用 `Mapped[Decimal]`/`Numeric`；API 层再按需要序列化为 float。增加 1/3、2/3、0/0 用例测试。

#### CR-11：终态汇总分类不准确且报告生成不幂等

**证据**

- `backend/app/services/worker_service.py:271-319` 在 execution 超时、停止或异常时，只要已有步骤且没有失败，就会把仍为 pending/running 的 case 标记为 passed。
- 未执行步骤没有被创建/标记 skipped，不符合 V1.1 停止规则。
- `_mark_terminal` 每次都新增 Report，没有查询更新或唯一约束。
- `reports.execution_id` 在模型和迁移中都不是 unique。
- Worker 轮询、timeout scan、heartbeat scan 可能并发终结同一个 execution。
- `backend/app/services/report_service.py:115-117` 使用 `scalar_one_or_none()`，重复报告会直接导致详情生成失败。

**影响**

执行状态可能是 error/stopped，但报告却显示用例 passed；并发终结还可能产生多个报告，使报告详情或下载返回 500。

**建议**

- 统一定义 case/step/assertion 状态归并表；中断时当前项 stopped/error、未执行项 skipped。
- `reports.execution_id` 增加唯一约束，使用 upsert 或 `SELECT FOR UPDATE` 幂等汇总。
- 用条件更新保证只有一个进程从非终态推进到终态并负责汇总。

#### CR-12：已取消的 queued 执行仍可能被已认领 Worker 启动

**证据**

- `backend/app/services/execution_service.py:115-125` 取消 queued 任务时根据已经加载的状态直接修改 execution 和 queue。
- `backend/app/services/worker_service.py:195-210` Worker 可先把 queue 认领并提交。
- `backend/app/services/worker_service.py:343-370` `run_execution` 加载后不检查 execution 当前是否仍为 queued，直接创建快照、抢占设备并改为 running。

**影响**

用户看到 cancelled 的任务在竞争窗口中仍可能启动，并将 cancelled 反写为 running，违反不可逆状态机。

**建议**

- Worker 开始前执行原子 `UPDATE executions SET status='running' WHERE id=? AND status='queued' RETURNING ...`，rowcount 为 0 立即结束队列项。
- queued 取消也使用条件更新，并让 queue 状态与 execution 状态在同一事务内变化。

#### CR-13：截图文件名可在 Agent 主机上形成任意路径写入

**证据**

- `agent/executor/actions.py:91-96` 直接使用用例中的 `filename`。
- `agent/executor/context.py:37-40` 将 filename 与截图目录拼接后直接交给 driver，没有 basename、绝对路径或 `..` 校验。
- `agent/main.py:55-61` 没有传入隔离的 execution screenshot 目录，默认目录为当前工作目录。
- 后端步骤结构又是任意字典，可通过 API 绕过当前 UI 的限制。

**影响**

项目成员可在运行真实 Appium 的 Agent 权限范围内，用 PNG 内容覆盖任意可写路径，影响 Agent 配置或其他本地文件。

**建议**

- 服务端忽略用户文件名或只接受展示名；实际名称使用 UUID。
- Agent 为每个 execution 创建临时隔离目录，resolve 后校验 `is_relative_to()`。
- 拒绝绝对路径、盘符、UNC、分隔符和 `..`。

### 4.3 P2 / 中

#### CR-14：前端退出和刷新令牌流程没有形成闭环

**证据**

- `frontend/src/stores/auth.ts:32-37` logout 只清 localStorage，不调用 `/api/auth/logout`，服务端 refresh token 仍有效。
- `frontend/src/utils/request.ts:33-40` 401 时直接清令牌，没有调用已经定义的 `refreshToken()`。
- `frontend/src/utils/request.ts:68-80` refresh 成功后只保存 access token；后端会撤销旧 refresh 并返回新 refresh，因此第二次刷新会失败。

**建议**

- logout 先尽力调用后端撤销 refresh，再清本地状态。
- 实现单飞 refresh 队列，保存后端返回的新 access + refresh，并重放原请求。
- 增加并发 401、刷新失败、登出后旧 token 不可用测试。

#### CR-15：前后端筛选参数不一致，分页 total 也未应用过滤条件

**证据**

- 前端用例发送 `status`，后端接收 `status_filter`：`frontend/src/api/cases.ts:68-78`、`backend/app/api/cases.py:31-57`。
- 前端执行发送 `status/type`，后端接收 `status_filter/execution_type`：`frontend/src/api/executions.ts:82-89`、`backend/app/api/executions.py:114-140`。
- 设备 API 类型发送 `status`，后端接收 `device_status`。
- 报告页发送 `status`，后端没有该参数；`keyword` 输入也从未发送：`frontend/src/views/Report.vue:15-25,51-56`。
- `backend/app/api/executions.py:125-142` 和 `backend/app/api/reports.py:46-72` 在附加过滤条件前构造 count query，导致 total 与 items 不一致。

**影响**

多个筛选控件看似可操作但实际无效，分页页数可能错误。

**建议**

统一 OpenAPI 参数名；前端类型从 OpenAPI 生成或至少建立契约测试。count 与 list 应从同一 filtered base query 派生。

#### CR-16：同一 Agent 重连时旧连接可能删除新连接

**证据**

- `backend/app/ws/managers.py:10-17` 新连接会替换字典中的旧连接并关闭旧 socket。
- 旧 handler 随后在 `backend/app/ws/routes.py:127-130` 调用 `disconnect(agent_id)`。
- `disconnect` 在 `backend/app/ws/managers.py:19-20` 不校验 socket 身份，直接 pop 当前映射，因此会把新连接删掉并标记 offline。

**建议**

`disconnect(agent_id, websocket)` 仅在当前映射仍等于该 websocket 时删除；在线状态也应与连接 generation/session ID 绑定。

#### CR-17：Agent 上报中消失的设备不会被标记离线

**证据**

- `backend/app/ws/handlers.py:62-90` 只新增或更新本次 payload 中出现的设备，没有处理数据库已有但本次缺失的设备。
- Worker 选设备依赖 Agent online + Device idle；旧设备可能一直保持 idle。

**影响**

拔出的设备仍可能出现在可用列表并被 Worker 选中，造成执行立即失败。

**建议**

每次完整设备快照后把未出现且未锁定的设备标记 offline；锁定设备消失时按失联路径终结执行。设备唯一键建议为 `(agent_id, udid)`。

#### CR-18：模块更新没有验证父模块归属或循环

**证据**

- `backend/app/api/elements.py:57-60` 创建模块时校验父模块属于当前项目。
- `backend/app/api/elements.py:73-89` 更新时直接赋值 parent_id，没有同样校验，也允许 self-parent 或形成循环。

**影响**

可建立跨项目层级或循环树，破坏模块导航与数据隔离语义。

**建议**

复用统一 validator，检查同项目、未删除、非自身且不会形成祖先循环。

#### CR-19：ORM 与迁移存在已确认的唯一约束漂移

**证据**

- 初始迁移包含 `UniqueConstraint('project_id', 'user_id')`。
- `backend/app/models/project.py:19-25` 的 `ProjectMember` 没有对应 `__table_args__`。
- `uv run alembic check` 实际报告将删除 `project_members_project_id_user_id_key`。

**影响**

后续开发者若信任 autogenerate 并应用迁移，可能误删防止重复成员的数据库约束。

**建议**

在 ORM 恢复 UniqueConstraint，并把 `alembic check` 加入 CI。循环外键警告属于已知设计，需要继续人工审阅迁移。

#### CR-20：公共项目报告在列表和详情权限上表现不一致

**证据**

- 报告详情通过 `get_project_permission`，允许公开项目 viewer 查看。
- `backend/app/api/reports.py:57-68` 未指定 project_id 时只列 owner/member 项目，不包含公开项目。
- 权威权限矩阵允许其他登录用户查看公开项目报告。

**影响**

用户若知道 report ID 可以查看，但无法在报告列表发现，权限体验不一致。

**建议**

明确产品规则后，让列表与详情使用同一可见项目子查询。

#### CR-21：部署安全基线未强制执行

**证据**

- `backend/app/core/config.py:21-24,37` 内置可工作的数据库密码、JWT secret 和 internal token 默认值。
- 启动时没有检查默认密钥、密钥长度、HTTPS 或生产环境标识。
- 设计文档要求登录、注册、执行创建限流，但依赖和中间件中没有限流实现。
- `min_agent_version` 已配置，但 Agent 注册流程未使用。

**影响**

遗漏 `.env` 时服务仍会以公开默认秘密启动；认证端点可被暴力尝试；旧 Agent 不会被拒绝或告警。

**建议**

增加 environment 模式；非 development 环境遇到默认 secret、非 TLS 或弱配置时拒绝启动。为认证、上传、执行创建加限流，并在注册时进行语义化版本比较。

#### CR-22：步骤与断言缺少后端契约和资源归属校验

**证据**

- `backend/app/schemas/case.py:7-24` 接收 `list[dict[str, Any]]`。
- 创建/更新用例不验证 action/type 是否存在、不验证必填参数、不验证 element_id 属于同一项目。
- Worker 收集元素时对找不到或非法 element_id 只是略过，错误延迟到 Agent。

**影响**

错误用例可以长期入库，执行时才失败；还会放大 Agent 本地路径等安全输入问题。

**建议**

引入共享版本化 Registry contract；后端严格验证动作/断言和元素归属，Agent 对未知字段继续保持防御性校验。

#### CR-23：前端主 chunk 体积偏大

**证据**

- 生产构建主入口约 1,127.96 kB，gzip 后约 376.22 kB，Vite 发出 chunk 超限警告。

**建议**

将 Element Plus 按需引入，配置 manualChunks 拆分 Vue/Element Plus/VueUse，并保留页面级动态 import。此项不阻塞功能修复。

#### CR-24：WebSocket 广播组空集合清理条件永远不成立

**证据**

- `backend/app/ws/managers.py:66` 使用 `if group and not group`，逻辑上永远为 false。

**影响**

发送失败移除最后一个 socket 后，空集合会残留在 `_groups`，长期运行可能积累无用 execution_id。

**建议**

改为 `if not group: pop(...)`，并增加广播失败后的连接组清理测试。

### 4.4 P3 / 低

#### CR-25：多个更新接口无法显式清空可选字段

`ProjectUpdate`、`ElementUpdate`、`CaseUpdate`、`SuiteUpdate` 使用 `None` 同时表示“未提交”和“清空”，实现又只在值非 None 时赋值。因此 description、page_name、module_id 等字段不能稳定地从有值更新为空。建议使用 `body.model_fields_set` 区分缺失和显式 null。

#### CR-26：报告 HTML 缓存存在崩溃恢复盲点

`backend/app/services/report_service.py:168-194` 发现 `report.html` 已存在时立即返回，不会确保 `reports.report_path` 已同步。若进程在写文件后、提交数据库前崩溃，后续下载虽成功，但列表会长期显示“按需”。建议命中缓存时也幂等同步 DB，或采用临时文件 + 原子 rename + DB 状态更新。

- 开发库已在 Alembic head。
- 19 张业务表和循环外键已按既定顺序建立。

## 6. 安全专项评价

### 6.1 信任边界

建议把以下主体明确视为互不信任：

- 普通用户与其他项目用户。
- public viewer 与项目 member。
- 每个 Agent 与其他 Agent。
- Agent 回传内容与 FastAPI 本地文件系统。
- Worker 内部接口调用者与公共网络调用者。

目前代码主要完成了“登录用户”和“已注册 Agent”的身份认证，但资源级授权没有覆盖所有入口。尤其 Agent PSK 不是资源授权，不能替代 execution-device-agent 绑定。

### 6.2 密钥处理建议

- JWT secret、internal token、Agent PSK 在生产环境必须由安全随机源提供并支持轮换。
- Agent PSK 数据库只存哈希；创建时一次性显示。
- 日志、异常、响应 schema 不得输出 PSK、refresh token 或 internal token。
- 前端 refresh token 存 localStorage 具有 XSS 放大风险；如果未来引入任何富文本/第三方脚本，应重新评估 HttpOnly Secure SameSite cookie 方案。

## 7. Agent 与执行正确性专项评价

### 7.1 建议的 Agent 并发模型

```text
WS receive loop
  ├─ register / heartbeat / device sync
  ├─ start_test → create_task(execution_task)
  └─ stop_test  → execution_task.cancel_event.set()

execution_task
  ├─ 创建 execution 专属临时目录
  ├─ 使用下发 device 构造 Appium options
  ├─ 每个步骤前后检查 cancel/deadline
  ├─ 截图 → HTTP 上传 → 返回对象键
  └─ finally: driver.quit + 临时文件清理
```

若一个 Agent 支持多个设备，应按 UDID 建 task/driver 映射；若 V1 暂不支持并发，则 Worker 必须按 Agent 而不是仅按 Device 加互斥约束。

### 7.2 状态机建议

- 所有状态变化走一个服务函数，输入为 `execution_id + expected_states + next_state + actor`。
- 使用条件 UPDATE 和 rowcount 实现原子转换。
- 晚到的 Agent 消息不能把 terminal 状态改回其他状态。
- `stopping` 必须有 deadline。
- 终态汇总只执行一次，并在同一事务中生成/更新报告、释放设备、完成队列。

## 8. 前端专项评价

### 8.1 功能完整性

页面结构和 UI 设计系统已经较统一，但用例编辑器是当前最明显的功能瓶颈。建议不要继续用单一“参数”输入框扩展，而应直接建立基于动作元数据的字段组件，否则前端、后端和 Agent Registry 会持续漂移。

### 8.2 建议增加的前端测试

当前前端没有自动化测试脚本。至少应增加：

- 路由：新建/编辑用例、报告详情、未登录跳转。
- API contract：status/type 参数名和分页结构。
- 用例编辑器：每种动作/断言生成正确 JSON。
- 会话：401 刷新单飞、刷新轮换、logout 撤销。
- 执行页：WS status/log/completed、断线重连、drawer 关闭清理。
- E2E：登录 → 新建项目 → 元素 → 用例 → Mock Agent 执行 → 报告。

## 11. 总体判断

该项目的基础架构和正常业务 CRUD 已达到可继续迭代的水平，Mock 联调链路也有较好的测试基础。当前风险集中在“从可演示 V1 到可信多人系统”的边界：权限、Agent 信任、真实设备执行、取消并发和报告数据可信度。

建议先暂停继续扩展 UI 页面或 V2 功能，以安全止血和执行闭环为一个独立加固 Step；完成后再做一次针对权限矩阵、Agent 协议和状态机的复审。
