## Step 2 — `_mark_terminal()` 改调纯函数 + 修复 N+1

**性质**：行为保持 + 性能优化。

### 2.1 批量化查询（本次新发现的性能问题）

**现状**（`worker_service.py:516-582`）：

```
for c in cases:            # N 条用例
    SELECT steps WHERE case_id = c.id          ← 每用例 1 次
    SELECT assertions JOIN steps WHERE ...     ← 每用例 1 次
    UPDATE assertions ... SET skipped          ← 每用例 1 次
    UPDATE steps ... SET skipped               ← 每用例 1 次
for suite in suites:       # M 条套件
    SELECT steps WHERE suite_id = suite.id     ← 每套件 1 次
    UPDATE steps ... SET skipped               ← 每套件 1 次
```

**100 用例 + 10 套件 ≈ 520 次数据库往返**，全部发生在持有 `finalized_at` CAS 锁的终态汇总路径上。

**改法**（每类各 1 条查询）：

```python
steps_by_case       = 分组(SELECT ExecutionStep       WHERE execution_case_id.in_(case_ids))
assertions_by_case  = 分组(SELECT ExecutionAssertion
                            JOIN ExecutionStep
                            WHERE ExecutionStep.execution_case_id.in_(case_ids))
steps_by_suite      = 分组(SELECT ExecutionStep       WHERE execution_suite_id.in_(suite_ids))
```

未执行行置 `skipped`：改为 **2 条批量 UPDATE**（用 `.in_(case_ids)` / `.in_(suite_ids)`），
替代循环内的 N+M 条。

> 注意 `case_ids` / `suite_ids` 可能为空列表，`.in_([])` 在 SQLAlchemy 中会产生 `WHERE false`，
> 行为正确但需保留现有的 `if case_ids:` 短路以避免无谓往返。

### 2.2 `_mark_terminal()` 瘦身

改造后的结构（**目标 ≤ 120 行**，当前 225 行）：

1. CAS 抢 `finalized_at`（`worker_service.py:478-488`，逻辑正确，**原样保留**）
2. 批量加载数据（3 条 SELECT）
3. 调 `execution_summary` 纯函数算出全部状态与统计（无 IO）
4. 写回 ORM 对象 + 2 条批量 UPDATE
5. 幂等插入 `Report`（`on_conflict_do_nothing`，保留）
6. 释放设备 / 队列置 `done` / `commit`

### 5.5 详细设计

`agent_ws` 目前在 `register` 成功**之前**就 `await websocket.accept()`（`ws/routes.py:150`），
且没有消息体大小与频率限制。已有 `validate_agent_message` 做协议校验（这部分是对的），缺的是连接层。

新增配置项（`config.py`）：

```python
agent_ws_max_frame_bytes: int = 1_048_576            # 1 MB
agent_ws_max_pre_register_messages: int = 20
agent_ws_register_timeout_seconds: int = 30
```

三重限制：
1. **单帧大小上限** —— 超限时 close(1009)
2. **register 前消息计数上限** —— 未 register 的连接最多收 20 条消息，超出即断开
3. **未 register 连接存活时长** —— 30 秒内未完成 register 即断开

> 阈值**先设宽松**（1MB / 20 条 / 30 秒）。这三条可能误伤弱网环境的 Agent，
> 建议上线观察一段时间后再收紧，不要一次性设成激进值。
