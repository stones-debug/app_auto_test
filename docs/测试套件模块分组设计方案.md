# 测试套件模块分组设计方案

> 目标：让「测试套件」像「测试用例」一样按模块（树形）管理，并支持把模块拖到另一个模块下成为其子模块。
> 状态：**设计方案，未实施**。文末列出需要拍板的决策点。
> 修订：2026-09-10

---

## 0. 结论速览

| 项 | 结论 |
|---|---|
| 数据结构 | `test_modules` 增加 `scope`（`case` / `suite`），用例树与套件树**各自独立**、结构规则完全一致；`test_suites` 增加 `module_id` |
| 为什么加 scope 而不是共用一棵树 | 删除/改名的语义边界清晰，且将来给套件模块加属性（默认档案、目标设备）不会污染用例侧。若想共用一棵树，只需去掉 scope 维度，成本是删几行代码 |
| 拖拽 | 抽公共组件 `ModuleTree.vue`，用原生 HTML5 DnD 实现三态落点（上方/下方/内部）；**用例页与套件页共用**，用例页顺带获得拖拽能力 |
| 后端接口 | 复用现有模块接口 + 新增 `scope` 参数；新增 `PUT /api/modules/{id}/position` 做原子移动（含兄弟重排）；现有 `PUT /api/modules/{id}` 已能改 `parent_id`，保留兼容 |
| 必须先修的 2 个既有缺陷 | ① 用例「未分组」筛选**当前完全失效**（点击后展示全部用例）② 套件列表**只显示前 20 条**。两者都与本设计强相关，建议同批修 |
| 执行 / 报告 / 档案解析 | **v1 不受影响**（套件模块只是组织维度，不进入执行快照） |
| 工作量 | 后端 1 个 Step（迁移 + 接口 + 测试），前端 1 个 Step（共享组件 + 两页接入 + 测试），文档小改 |

### 1.2 套件侧：完全没有模块概念

- `TestSuite`（`backend/app/models/case.py:43-60`）字段只有 `project_id / name / description / status / setup_steps / teardown_steps`，**没有 `module_id`**。
- `GET /api/projects/{pid}/suites`（`backend/app/api/suites.py:28-50`）只支持 `keyword`、`status`；仓储 `list_page`（`backend/app/repositories/suites.py:33-61`）固定按 `updated_at desc` 排序，无模块过滤。
- 前端 `frontend/src/views/Suite.vue:316-380` 是「左侧套件列表 + 右侧详情」，左侧列表来自 `useSuiteList`（`frontend/src/composables/useSuiteList.ts:45-53`），**客户端**做关键字过滤和排序。
- 唯一与"模块"有关的痕迹是**用例编排里展示用例所属模块名**：`SuiteCaseOut.module_name`（`backend/app/schemas/suite.py:87`）、`SuiteModuleGroup.vue`（用于 `SuiteCasePicker` 把候选用例按模块分组）。这属于用例侧数据，与本设计无关，**不要改动**。

### 1.3 拖拽现状：全仓没有模块拖拽

全前端只有 3 处拖拽，都是 `vuedraggable`（SortableJS）用于**列表排序**，不涉及树：

```
src/components/CaseFlowEditor.vue:3   import Draggable from 'vuedraggable'
src/components/CaseStepEditor.vue:4   import Draggable from 'vuedraggable'
src/views/Suite.vue:5                 import Draggable from 'vuedraggable'   # 用例编排排序
```

所以「可以拖动模块」对**用例页也是新能力**，不是"已有能力搬过来"。本设计把它做成共享组件，两页同时获得。

### 1.4 ⚠️ 已核实的两个既有缺陷（与本设计强相关）

#### 缺陷 1：用例「未分组」筛选失效（P1）

三处证据链：

1. `frontend/src/views/Case.vue:70` 注释写着「未分组：后端按 module_id=null 过滤」，`Case.vue:86` 真的传 `module_id: null`。
2. axios 1.19 **会丢弃值为 `null` 的参数**（实测：`axios.getUri({url:'/a',params:{module_id:null,keyword:''}})` → `/a?keyword=`），所以该参数根本没发出去。
3. 后端 `app/repositories/cases.py:59-60` 是 `if module_id is not None: 过滤`，`None` 表示**不过滤**。

→ 结论：**点击「未分组」实际展示的是全部用例**。而且全仓没有任何代码能表达 `module_id IS NULL`
（`grep "module_id.is_" app/` 为空，`module_id=-1` 会命中不存在的 id 返回空列表）。也没有测试覆盖这个筛选。

本设计的模块树必须包含「全部 / 未分组 / 具体模块」三态，所以**必须先把这条修掉**，否则套件树会照抄同一个坑。

#### 缺陷 2：套件列表只显示前 20 条（P1）

`frontend/src/api/suites.ts:57-60` 的 `listSuites(projectId)` 不传任何分页参数 → 后端 `get_pagination`（`backend/app/utils/pagination.py`）默认 `page=1, page_size=20`，`list_page` 里 `.offset().limit()` 生效 → 第 21 个及以后的套件**在页面上根本看不到**，左侧的「N 个」计数也是错的。

加入模块树后列表要按模块过滤，客户端只有 20 条就会给出错误结果（某个模块明明有套件却显示空），所以**必须同批修**。

另外 `frontend/src/api/elements.ts` 的 `listModules(projectId, parentId)` 有个语义陷阱：传 `parentId === null` 会发 `parent_id=0`，而后端接口（`app/api/elements.py:66-78`）把 `parent_id == 0` 归一为 `None`，即**返回该项目全部模块**而不是"根层级"。当前所有调用点都不传第二参，所以没出问题，但 `0` 既当"未指定"又当"根层级"很含混——实施时保留了既有语义（避免破坏兼容），另加显式 `root_only=true` 表达"只要根层级"。

## 2. 目标与非目标

### 2.1 目标

1. 套件页有与用例页**外观与交互一致**的模块树：全部 / 未分组 / 多层模块、展开折叠、悬停操作、右键菜单。
2. 选中模块后，套件列表只显示该模块下的套件，支持搜索与排序。
3. 可以把**模块拖到另一个模块上/下/内**：同级重排 + 变更父级（reparent）。
4. 拖拽在用例页与套件页行为一致，共用同一份实现。
5. 非法目标（自身、自己的子孙）在**前端就不给落点提示**，后端仍做权威校验。

### 2.2 非目标（本次不做）

- 不改元素库的页面分组（`ElementGroup` / `page_name` 是另一套机制，`frontend/src/views/Element.vue` 那棵树不动）。
- 不把套件模块写进执行快照 / 报告（见 §8）。
- 不做模块级权限、不做跨项目移动、不做模块排序快捷键。
- 不做触屏/移动端拖拽（HTML5 DnD 在触屏无效；用「移动到…」菜单兜底，见 §6.5）。
- 不调整模块层级深度上限（现状无限制，与用例保持一致）。

## 3. 关键决策点（含推荐）

### 决策 1：套件模块树放在哪张表？★核心

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | `test_modules` 加 `scope`（`case`/`suite`），两张逻辑树物理同表；`test_suites.module_id` 只能指向 `scope='suite'` 的模块 | 树规则（循环校验、软删、排序、删除时子级提升）100% 复用；两侧删除/改名互不影响；将来给套件模块加字段不污染用例侧；回滚只需删列删行 | 需要 scope 隔离校验，防串（约 10 行代码） |
| B | 共用一棵树：只加 `test_suites.module_id`，不加 scope | 改动最小；"按业务模块归类"心智直接；一个模块下同时有用例和套件 | 语义耦合；用例树通常按页面/功能切得很细，套件按批次切，共树会让套件页出现大量空模块；将来想拆开需要数据迁移 |
| C | 新建 `test_suite_modules` 表 + `test_suites.suite_module_id` | 隔离最彻底 | 重复实现一整套 CRUD/循环校验/接口/前端组件；用户视角「模块」概念分裂成两个名字，认知成本更高 |

**推荐 A。** 若主人更想要「用例和套件共用同一棵树」，把 A 里的 `scope` 维度整体删掉即可（列不加、过滤不加、校验不加），前端组件照用——这是一个只减不增的简化，随时可切。

可选增强（A 之上）：套件模块树支持**一键复制用例模块结构**，兼顾"想共用结构"的诉求。

### 决策 2：拖拽用哪种实现？

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 抽 `ModuleTree.vue`，用原生 HTML5 DnD（`draggable` / `dragstart` / `dragover` / `drop`），自行判定三种落点 | 外观 100% 保持（主人要求"保持一样的树形结构"）；零新增依赖；`vuedraggable` 是列表排序封装，做树的三态落点很别扭；逻辑集中、可抽纯函数单测 |
| B | 换 Element Plus `el-tree` 的 `draggable` + `allow-drop` | 落点反馈开箱即用、支持过滤；但要重写现有树的模板与样式（右键菜单、文件夹图标、悬停操作都要走 slot），视觉会变，且 `el-tree` 的内部 DOM 结构会让现有 CSS 全废 |
| C | 递归 `<Draggable>` 嵌套 | SortableJS 的嵌套 group 控制"内部/前后"很脆弱 |

**推荐 A。** HTML5 DnD 的触屏短板用「移动到…」菜单兜底（§6.5）。

### 决策 3：选中父模块时，是否包含子孙模块的套件？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | 包含子孙（`module_id` + 其整棵子树）。符合直觉：点「登录」能看到「登录/验证码」下的用例 |
| B | 仅直接归属（与用例页现状一致：`app/repositories/cases.py:60` 是等值比较） |

**倾向 A**，但 A 要同步改用例侧（否则两页行为不一致），成本是多一次子树展开查询（模块表很小，可一次拉全量在内存里展开）。若主人倾向先对齐现状，选 B，行为与用例页当前完全一致，代价是"父模块看起来是空的"这种常见困惑会保留。

### 决策 4：拖拽是否同时给用例页开？

**推荐：开。** 主人要求"跟用例一样"，若只给套件开，两棵树的交互又不一致了。组件上加 `draggable` prop，默认开启；若要只给套件开，改一个 prop 即可。

## 5. 后端接口设计

分层遵循 `docs/...实施方案.md` §10.16：API 只做参数编排与权限，Service 负责事务与规则，Repository 负责 SQL；WS/API 不直接操作 Session。

### 5.1 模块接口（扩展现有，保持向后兼容）

| 方法 | 路径 | 变更 |
|---|---|---|
| GET | `/api/projects/{pid}/modules` | 新增查询参数 `scope: str = "case"`（只允许 `case`/`suite`）。**不传时行为与今天完全一致**（返回用例模块） |
| POST | `/api/projects/{pid}/modules` | `ModuleCreate` 增加 `scope: str = "case"`；`parent_id` 必须与 `scope` 匹配 |
| PUT | `/api/modules/{id}` | 不变（改名 / `parent_id` / `sort_order`）；`parent_id` 校验加上 scope 一致性 |
| DELETE | `/api/modules/{id}` | 语义按 scope 收窄：子模块提升到祖父级；`scope='case'` → 模块内用例置未分组；`scope='suite'` → 模块内套件置未分组 |
| **PUT** | **`/api/modules/{id}/position`** | **新增**，拖拽专用，见 §5.2 |

`ModuleOut` 增加 `scope` 字段（前端按 scope 区分数据源，避免串树）。

`GET` 的 `parent_id` 语义收紧（可选，建议做）：

- 现状：`parent_id` 传 `0` → 返回空数组（`app/repositories/elements.py:24-33`）。
- 建议：`parent_id` 传 `0` 视为"根层级"（`parent_id IS NULL`），与 `element_service.validate_parent` 里 `parent_id in (None, 0)` 的既有约定对齐；前端 API 封装同步改为只在显式需要时下发。

### 5.2 新增：拖拽移动接口（原子操作）

```
PUT /api/modules/{module_id}/position
body: { "parent_id": 3 | null, "before_id": 7 | null }
→ 200  [ModuleOut, ...]        # 返回该项目该 scope 的完整模块列表（扁平），前端直接替换
```

语义：把 `module_id` 移动到 `parent_id` 下，排在 `before_id` **之前**；`before_id = null` 表示追加到末尾；`parent_id = null` 表示移到根层级。

**为什么单独开接口，而不是让前端算好 `sort_order` 再 `PUT /modules/{id}`？**

1. 兄弟次序要重排成连续值（`0..n-1`），前端算 `(a+b)/2` 会浮点漂移、并发下错位；
2. 一次拖拽同时影响**两个父级**（源父级少一个、目标父级插一个），`PUT` 只能表达单行更新；
3. 后端能在一个事务里完成"校验 + 重排 + 提交"，失败不留半成品。

服务层骨架：

```python
async def move_module(db, *, module: TestModule, parent_id: int | None, before_id: int | None) -> list[TestModule]:
    # 1) 锁住同项目同 scope 的模块行，避免并发重排错位
    modules = await elements_repo.load_modules_for_update(db, project_id=module.project_id, scope=module.scope)
    by_id = {m.id: m for m in modules}
    # 2) 权威校验：父级存在、同项目、同 scope、非自身、非自身子孙（复用 validate_parent 的循环检测）
    await validate_parent(db, project_id=module.project_id, scope=module.scope,
                          parent_id=parent_id, module_id=module.id)
    if before_id is not None and before_id not in by_id:
        raise api_error(404, ErrorCode.NOT_FOUND, "目标位置不存在")
    if before_id in descendant_ids(modules, module.id):
        raise api_error(400, ErrorCode.INVALID_PARENT, "不能移动到自己的子模块内")
    # 3) 目标父级下的兄弟（排除被移动的模块），按 (sort_order, id) 稳定排序后插入
    siblings = [m for m in modules if m.parent_id == parent_id and m.id != module.id]
    siblings.sort(key=lambda m: (m.sort_order, m.id))
    index = len(siblings) if before_id is None else next(
        (i for i, m in enumerate(siblings) if m.id == before_id), len(siblings)
    )
    siblings.insert(index, module)
    module.parent_id = parent_id
    for order, item in enumerate(siblings):
        item.sort_order = order
    # 4) 源父级剩余兄弟也重排一遍，避免留下空洞（可选但更整洁）
    await elements_repo.renumber_siblings(db, project_id=module.project_id,
                                         scope=module.scope, parent_id=old_parent_id)
    await asset_service.commit_asset_change(db, [module.project_id])
    return await elements_repo.list_modules(db, project_id=module.project_id, parent_id=None, scope=module.scope)
```

**幂等性**：同一目标位置重复提交同一模块 → 结果相同（顺序不变），前端重复触发不会错乱。

### 5.3 未分组：把「不过滤」和「未分组」显式分开

推荐契约（三个互斥状态，不用魔法值、不依赖参数序列化细节）：

| 场景 | 请求 |
|---|---|
| 全部 | 不传 `module_id`、不传 `ungrouped` |
| 未分组 | `ungrouped=true`（后端加 `col IS NULL` 条件） |
| 某个模块 | `module_id=<id>`（决策 3 若选 A，后端展开为 `module_id IN (子树 ids)`） |

- `GET /api/projects/{pid}/cases` 与 `GET /api/projects/{pid}/suites` 都加 `ungrouped: bool = False`；
- 仓储层加显式分支（`app/repositories/cases.py:59` 与 `suites.py` 的同款位置）：
  ```python
  if ungrouped:
      conditions.append(TestCase.module_id.is_(None))
  elif module_id is not None:
      conditions.append(TestCase.module_id.in_(module_ids))
  ```
- 前端 `frontend/src/utils/caseModuleNavigation.ts` 的 `moduleQuery(key)` 从 `{module: key}` 改为把三态映射成 `{module: 'none'|'all'|<id>}`（URL 友好、刷新可还原），再由各页面把它翻译成 `ungrouped` / `module_id` 请求参数。

### 5.6 错误码

**现状（已核实）**：模块接口走的是普通 `HTTPException(status_code=..., detail="中文串")`（`app/api/elements.py:60-104`、`app/services/element_service.py:40-52`），**没有**用 `app/core/errors.py` 的结构化错误码；`ErrorCode`（`app/core/errors.py:9-44`）里也没有模块相关的码。这与第 10.15 节「HTTP 机器可读错误码」的口径不一致，属既有欠账。

本设计的处理：

- **新增的 `/position` 接口使用结构化错误**：在 `ErrorCode` 增加下列常量，用 `api_error(status_code, code, message, context)`（`app/core/errors.py:74`）抛出；
- **存量模块接口本次不改造**，避免在一个 Step 里混入与需求无关的返工；统一结构化改造列为后续独立清理项（会牵动 `tests/test_elements.py` 的断言）。

|---|---|---|
| 父模块不存在 / 跨项目 / scope 不匹配 | 404 / 400 | `MODULE_NOT_FOUND` / `MODULE_SCOPE_MISMATCH` |
| 父模块是自身或自己的子孙 | 400 | `MODULE_PARENT_INVALID` |
| `before_id` 不属于目标父级 | 400 | `MODULE_POSITION_INVALID` |
| 套件的 `module_id` 指向用例模块 | 400 | `MODULE_SCOPE_MISMATCH` |

### 6.3 拖拽状态机

**三态落点判定**（`resolveDropPosition`）：以行为单位，指针落在行的上 25% → `before`、下 25% → `after`、中间 50% → `inside`（成为子模块）。行高从 `getBoundingClientRect().height` 取，不硬编码。

**落点计算**（`planModuleMove`，纯函数）：

```ts
export interface DropTarget { moduleId: number; position: 'before' | 'after' | 'inside' }
export interface MovePlan { moduleId: number; parentId: number | null; beforeId: number | null }

/** 返回 null 表示落点非法（自身 / 自身子孙 / 结果与当前一致），前端不显示提示线。 */
export function planModuleMove(flat: TestModule[], draggedId: number, target: DropTarget): MovePlan | null
```

规则：

| 落点 | `parentId` | `beforeId` |
|---|---|---|
| `inside` on X | `X` | `null`（追加到 X 的子级末尾） |
| `before` on X | `X.parent_id` | `X.id` |
| `after` on X | `X.parent_id` | X 在兄弟中的下一个同父节点 id，无则 `null` |

再加一个**根层级落区**：树底部一条"拖到此处成为顶级模块"的放置带（`parentId=null, beforeId=null`），否则顶层模块只能互相排序、无法把子模块提出来。

**视觉反馈**：

- 拖起后源行 `opacity: .5`；
- `before` / `after` → 目标行上/下边缘 2px 高亮线（伪元素，不引起跳动）；
- `inside` → 目标整行描边 + 浅色底；
- 非法 → 不显示任何提示，光标 `not-allowed`；
- drop 后**乐观更新**（本地先改树）→ 调 `moveModule` → 失败则整体回滚 + `ElMessage.error`。

**实现细节**：`dragstart` 里写 `dataTransfer.setData('text/plain', String(id))`（Firefox 必须写数据才启动拖拽），`dragover` 里 `preventDefault()` 才能接收 `drop`；拖动超过 5px 才进入拖拽态，避免与"点击选中"打架。

### 6.4 套件页布局

现状是两栏（`el-col :lg="9"` 左列表 + `:lg="15"` 右详情）。加树有两种排法：

**方案 A（推荐，改布局最小）**：左栏内部纵向分为"模块树（可折叠）+ 套件列表"，树区 `max-height: 40%`、超出滚动，默认只展开根级；列表占据剩余高度。

│       · 验证码                                               │
│   ▸ 下单模块                                                 │

├──────────────────────────────────────────────────────────────┤
│ 搜索框            排序 ▾                                     │
│ ┌ 冒烟套件 ──────────────────────── 12 个用例 / 2 分钟前 ─┐ │

**方案 B**：三栏（模块树 6 栏 | 套件列表 8 栏 | 详情 10 栏）。信息密度高但 1440px 以下会挤，详情区可读性下降。不推荐作为 v1。

树的折叠状态按 `project:scope` 存 `localStorage`，刷新后保持。

### 6.5 触屏与键盘兜底：「移动到…」

HTML5 DnD 在触屏浏览器不生效，且拖拽没有键盘等价操作。因此右键菜单与操作栏里提供 **「移动到…」**：弹出对话框（`el-tree-select` 选目标模块，含"根层级"）→ 复用同一个 `/position` 接口，`before_id=null`（追加到目标末尾）。

一举三得：触屏可用、键盘可达、拖拽失灵时有退路。**这是必做项，不是可选。**

### 6.6 套件列表按模块过滤

- 选中「全部」→ 不传 `module_id` / `ungrouped`；
- 选中「未分组」→ `ungrouped=true`；
- 选中具体模块 → `module_id=<id>`（决策 3 选 A 时后端自动含子孙）；
- 同时把 `keyword` 一并下发给服务端（后端已支持），避免只在已加载的一页里搜；
- `page_size=200`（`settings.max_page_size = 200`）。若返回条数正好等于 200，在列表底部提示「仅显示前 200 个，请用搜索缩小范围」，并把客户端 `sortBy` 置灰（因为排序只作用于已加载集合，语义已经不可靠）。
- 后续改进项（不在本次范围）：`GET /suites` 支持服务端 `sort` 参数 + 前端无限滚动。

## 8. 影响面分析：为什么执行 / 报告 / 档案不受影响

已核实的链路：

- **模块当前只有两个用途**：① 用例列表的筛选与展示（`app/repositories/cases.py:75-81`）；② 快照里带一份模块名——`ExecutionCase.module_name`（`app/models/execution.py:159`），由 `profile_resolver`（`app/services/profile_resolver.py:362-364, 641`）在准备快照时写入，供报告展示「用例来自哪个模块」。
- **`ExecutionSuite`（`app/models/execution.py:101-139`）没有 `module_name`**，只有 `suite_name` 快照。
- 归档解析 `app/repositories/app_profiles/resolution.py:150-153` 的 `get_project_modules` 只把模块当**名字字典**用，不做规则匹配（档案的 skip/override 是按 `(suite_id, case_id, node_key)` 定位，见第 10.18 节），所以新增"套件模块"不会改变任何解析结果。

结论与决策：

1. **v1 不把套件模块写进执行快照**。报告里套件本来就按 `suite_name` 展示，加模块维度收益低、改快照结构成本高。
2. 用例侧的模块改名会改变 `ExecutionCase.module_name`，所以模块写操作继续走 `commit_asset_change` 推进资产 revision（现状如此，不动）。
3. 套件模块改名/移动同走 `commit_asset_change`（保持心智一致）。若将来确认不需要，可以只 `db.commit()`，属于纯优化。
4. 后续若要「报告按模块分组套件」，需要给 `ExecutionSuite` 加 `module_name` 快照字段 + 迁移 + 前端分组——**单独立项**，本次不做。

### 13.4 与设计方案的差异（均已在实施中确认合理）

1. **删除模块时两侧都解绑**（用例与套件各一条 UPDATE），而不是按 scope 只解绑一侧——正常数据下等价，多这一条是为了兜住历史上可能存在的脏数据，代价极低。
2. **套件列表关键字也匹配描述**：搜索从客户端移到服务端后，为保持原有“按名称或描述搜索”的提示语，`list_page` 的 `keyword` 改为 `name ILIKE OR description ILIKE`（附带一条测试）。
3. **套件模块也能在编辑对话框里改**：原方案只提到“拖拽模块”，但套件本身也需要能换模块，否则“套件分模块管理”只完成一半。
4. **`el-option` 不接受 `null`**：套件对话框的“未分组”用 `0` 作为哨兵值（`el-select` 也不加 `clearable`，否则清空会把 `modelValue` 变成 `''` 并原样发给后端）。
5. **模块 API 从 `api/elements.ts` 抽到 `api/modules.ts`**：套件页引用 `elements.ts` 语义不清晰；旧导出保留为 re-export，未产生额外改动面。
